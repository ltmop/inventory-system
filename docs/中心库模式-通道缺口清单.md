> 起因：2026-09-14 owner 反馈「设置里一堆功能不能用」：**收款码无法上传、手机看店扫码没通过、官网未链接、

## 0. 一条不变量（判断"这个功能在中心库模式下能不能用"的唯一标准）

**渲染层会调用的每个通道，必须落在三者之一：**

| 归属 | 判定 | 谁来服务 |
|---|---|---|
| ① 业务通道 | 出现在 `electron/server.js` 的通道表里 | 中心库那台服务器（`app.junchengzn.com/api/invoke`） |
| ② 本机前缀 | `src/lib/api.ts` 的 `LOCAL_ONLY_PREFIXES`（`cloud:` `update:` `site:`） | 这台电脑（IPC） |
| ③ 本机名单 | `src/lib/api.ts` 的 `LOCAL_ONLY_CHANNELS`（逐个点名） | 这台电脑（IPC） |

**三者都不在 = 中心库模式下必然 404 `unknown channel`** → 渲染层 `.catch` 一吞 → 用户看到「点了没反应」。
这就是本次那一堆症状的机制，跟 9/14 早先修的「已登录却显示未登录」「点下载更新没反应」是同一类。

判定"该归谁"只看一句话：**这个通道的答案，中心库那台服务器上有没有？**
- 没有（问本机：路径、局域网服务、授权、麦克风、收款码图片…）→ 加进 ③
- 有（哪怕语义上看起来重复）→ 留在①，别加

闸门：**`npm run check:channels`**（`scripts/verify-channel-routing.mjs`）——
它从源码里枚举渲染层真正调用的通道，和 `server.js` / 本机表交叉比对，并强制两条纪律：
① 出现未归属的通道立刻红；② 缺口清单只能变短不能变长（修好一个必须从清单里删掉，
否则「清单与实际缺口必须完全一致」这条会红）。

重新算出当前缺口：

```
node scripts/verify-channel-routing.mjs
```

## 1. 本次修的：35 个通道归本机（症状 → 根因）

| owner 看到的现象 | 真正的根因 | 修法 |
|---|---|---|
| **收款码无法上传** | `payment:saveQr` / `payment:deleteQr` 中心库上没有（只有给手机用的 `payment:getQr`）→ 上传打到服务器 404。**注意 `payment:record` 是记账，必须留在服务端**，所以只能逐个点名、不能按 `payment:` 前缀一刀切 | 三者归本机（收款码是本机图片文件，手机端由本机局域网服务读同一份） |
| **手机看店扫码没通过** | 双重：① `server:status/toggle/regenerateToken` 中心库上没有 → 卡片读不到状态，二维码块根本不渲染；② 二维码编码的是 `https://ip:17533`（**自签证书**），微信内置浏览器不给点「继续访问」，扫了直接打不开 | ① 三者归本机；② 看店二维码改用 **http** 地址（只看账不需要 https）；卡片上「服务地址」原来显示的是 `http://ip:<https端口>`，也是错的，一并改成真实 http 地址 |
| **官网未链接** | `electron/main.js` 里 `setWindowOpenHandler(() => ({ action: 'deny' }))` 把渲染层 `window.open` **一律拒掉**（防钓鱼窗口的既有设计），点了等于没反应；正确出口 `app:openExternal` 又不在本机表里 → 中心库模式下还会打到服务器 | 新增单一出口 `openExternalUrl()`（走 `app:openExternal`），`app:openExternal` / `app:info` 归本机；`SiteContactCard`、`HelpPage` 都改用它 |
| **意见反馈邮箱没用** | ① `feedback:send` 中心库上没有 → 提交失败（404 被吞）；② 那个「接收地址」**只支持飞书机器人 https 地址**，填邮箱进去只会静默存本机 —— 而卡片上一个字都没说 | ① 归本机；② 输入框改成明确的「飞书机器人地址（必须是 https://…）」+ 写明"填邮箱没用"；③ 新增「复制内容」按钮，并把我们的客服微信/邮箱（来自 `site:contact` 单一事实源）显示出来 |
| **关于里仍是本地单机部署** | `SettingsPage.tsx` 写死的文案 | 改为按真实配置拼：`中心库模式（https://app.junchengzn.com）· 多台电脑共用一份账` / `本地单机部署 · 数据只在这台电脑上` |

归本机的完整清单（37 个，逐个都写了理由）见 `src/lib/api.ts` 的 `LOCAL_ONLY_CHANNELS`。
附带两处：
- `friendlyChannelError()`：以后再有通道打到服务器 404，界面显示的是
  「『xxx』这个功能在中心库模式下还没开通…」而不是一句英文 `unknown channel`。
- `openExternalUrl()` 明确**不再**用 `window.location.href` 兜底（HelpPage 原来是那么写的，
  那会把整个应用窗口导航到外站，回不来）。

## 2. 还没修的：27 个缺口（**不能**靠"归本机"解决）

这些通道都**带账本语义**：一旦归本机，客户端会去读**这台电脑那份旧库**，
结果是「看起来正常、数字是错的」——比报错危险得多。所以只能**补服务端**（`electron/server.js` 的
`INVOKE_CHANNELS` + `WRITE_CHANNELS`），再按红线⑦的流程部署（先备份、只部署产物）。

| 前缀 | 通道 | 为什么不能本机化 | 建议 |
|---|---|---|---|
| `ai:` | `smartSearch` `analyzePhoto` `parseInboundNote` | 要搜/匹配商品库 | 服务端补（本地兜底算法同码，可直接复用） |
| `user:` | `login` `logout` `current` `list` `create` `update` `delete` `setStaffLogin` `staffLoginEnabled` | 员工账号是"店"的，不是"这台电脑"的；本机化会让两台机账号不一致 | 服务端补（或按 I0-2/I0-3 的成员体系走）；**这是最要紧的一组 —— 中心库模式下现在员工登不上** |
| `priceTier:` | `set` `delete` | 价格档是店级账本数据 | 服务端补 |
| `unit:` | `create` `update` `delete` `move` | 单位是店级账本数据（服务端只有 `unit:list`） | 服务端补 |
| `knowledge:` | `list` `save` `update` `delete` | 知识库是店级数据 | 服务端补 |
| `category:` | `listWithCount` | 分类计数要读账本 | 服务端补 |
| `clearance:` | `get` | 清仓建议读库存 | 服务端补 |
| `pricing:` | `get` | 定价建议读成本/售价 | 服务端补 |
| `template:` | `list` `apply` | 模板作用于整个账本 | 服务端补 |

## 3. ⚠️ 更要紧的事：**线上中心库服务端落后于仓库**

2026-09-14 直接读线上 `/opt/inventory-app/electron/server.js`（sha256 `e5eb0554…`）与仓库对比：

| | 仓库有 | 线上有 |
|---|---|---|
| `category:create` `category:rename` `category:delete` `category:move` `category:setParent` | ✅ | ❌ |
| `priceTier:set` `priceTier:delete` `priceTier:list` | ✅ | ❌ |

**后果：中心库模式下「分类管理」改不了、价格档也用不了**（即使客户端完全正确）。
原因看 `docs/发布记录.md` 的部署顺序一节：9/13 那次服务端更新只部署了
`channels.js`、`db.js`、`commands/outbound.js`，**没部署 `server.js`** —— 而通道表就在 `server.js` 里。

**所以"补服务端"是两件事**：① 先把仓库里这份 `server.js` 部署上去（补齐已存在的差）；
② 再为新分析的 27 个缺口写实现。两件都要按红线⑦走：**先备份再覆盖、只部署产物**。
