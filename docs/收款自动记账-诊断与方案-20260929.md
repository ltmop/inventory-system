# 收款自动记账 · 诊断与方案 · 2026-09-29

> 起因：客户反馈「微信收款和支付宝收款没有连在 App 上，每次都要手动去录入」。
> 本文档回答两件事：① 现在钱是在哪一步被记丢的 ②「真接微信支付宝」到底能不能做。

---

## 一、诊断：一半痛点是我们的重复记账（已核验）

### 事实链

| 步骤 | 位置 | 结果 |
|---|---|---|
| 1 老板在开单页点「微信」 | `electron/mobile/pages/pos.js:1020` | 弹出已配置的收款码 |
| 2 顾客扫码付款 | — | 钱进老板自己的微信 |
| 3 老板点「已完成收款」 | `pos.js:1020` | 调 `outbound:checkout({ payMethod:'微信' })` |
| 4 落库 | `electron/commands/outbound.js:258` | `transactions.pay_method = '微信'`（含金额） |

**到这一步，每一笔实收的方式和金额都已经在库里了。**

### 但这一步把数据丢了

```js
// electron/commands/receipt.js:53  reconcileReceipt()
const regs = db.prepare(
  'SELECT method, amount FROM payment_registers WHERE register_date = ?'
).all(d)
```

实收**只认 `payment_registers` 一张表**。全库检索确认：这张表只有 `registerReceipt()`
一个写入方，即**纯手工登记**，不存在任何自动写入路径 —— `transactions.pay_method`
从头到尾没被读过一次。

结果：老板每天收摊还要去「更多 → 收款登记明细」→ 选日期 → 手打当天微信/支付宝/现金总额。

> 客户说的「每次都要手动录入」，指的就是这一步。而那笔金额系统早就有了，只是没人去取。

### 顺带查出的两个隐患

1. **重复登记会静默丢钱**（`receipt.js:16`）
   `ON CONFLICT(register_date, method) DO UPDATE` —— 同一天同方式重复登记是**覆盖**不是累加。
   上午录一次、下午录一次，第二次把第一次吃掉，没有任何提示。
2. **差异无法归因**
   差异长期不为 0 又看不出为什么，老板看几次就不会再看 —— 这个功能会沦为摆设。

## 二、方案：先做不依赖任何外部授权的那一半

### 推荐（本周，合计约 2 天）

| # | 改动 | 工时 |
|---|---|---|
| 1 | 服务端加「按日汇总收银台实收」查询（`transactions` 按 `pay_method` 分组求和） | 0.5 天 |
| 2 | 手机端登记面板加「按收银台预填」——显示合计金额，点一下自动填进输入框 | 0.5 天 |
| 3 | 顺手修：重复登记改为「累加」，或提示「今天已登记 ¥xxx，追加还是覆盖？」 | 0.5 天 |
| 4 | 桌面端 `ReceiptReconcilePage` 同步显示「自动带回」一行，两端同口径 | 0.5 天 |

**关键取舍：口径先不动。**
`payment_registers` 的现有语义保持不变 → 历史数据零风险 → 改坏了也能一键回退。

### 目标口径（改这个必须先拍板）

```
实收 = Σ transactions.pay_method（收银台自动带回）
     + payment_registers（另收补登，语义改为「App 开单之外的钱」）
```

⚠️ **不能现在直接切**：店里过去手填的金额，有一部分填的是「含收银台的总额」。
一旦让 `transactions` 也参与计算就会**双计**，老板第二天会看到一个巨大的假差异。
切之前必须做一次历史数据校准（把存量登记金额拆成「已含收银台 / 纯补登」两类）。

## 三、「真接微信支付宝」的技术现实 —— 取决于客户用哪种码

> 这一节要原样讲给客户听。市面上号称「能同步个人码流水」的，要么是灰色手段，
> 要么本身就要求商户资质。别让我们看起来像在糊弄，也别承诺做不到的东西。

| 客户用的 | 能不能自动 | 具体说明 |
|---|---|---|
| **个人收款码**（大多数小店） | **不能** | 微信/支付宝不向任何第三方开放个人码流水查询接口 —— 是平台规则，不是技术问题。能对上的办法 = 模拟登录 / 爬后台：违规、有封号风险、随时失效，**不做** |
| **商户收款码** | 能 | 微信支付商户平台 / 支付宝开放平台有官方账单接口。前提：营业执照 + 商户号 + 开通 API 权限 + 接口证书 + 常驻服务端。**账单是 T+1**（今天只能拉昨天的），要实时得另接支付回调。开发 1.5–2 周，资质这一关卡在客户身上 |
| **聚合支付服务商**（收钱吧 / 拉卡拉 / 移卡） | **唯一能真自动** | 给开发者开放订单查询与收款回调：顾客付一笔 → 实时推给我们 → 自动对上当日应收。代价：费率 0.25%–0.38% + 客户签约（可选配云喇叭播报）。值不值由客户自己算这笔账 |

**怎么判断客户是哪一种：**
微信里「收付款 → 二维码收款」自己生成的那张、或存在相册里的静态码 —— 基本就是个人码。

**卡住一切的那句话（必须去问）：**
> 「你们店里收钱，用的是自己微信里那个个人收款码，还是微信支付的商户号？」

这个问题答案决定后续是「能接」还是「只能做到最少录入」，代码里查不出来。

## 四、边界（没做 / 没验）

- 只做了静态代码读取证据，**没有改任何实现**，也没连真库验证数值。
- 上文出现的金额（¥1,286.00 / ¥986.00 等）都是**示例数据**，不是客户真实金额。
- 没调研具体哪家聚合服务商的接口与费率上限；真要接得先拿客户意向再谈。
- 历史数据校准的具体算法没写 —— 要等确认「切换目标口径」之后再设计。
