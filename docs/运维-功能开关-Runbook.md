# 运维 Runbook：功能开关（Feature Flag）

> 2026-09-15 落地（对应 `docs/桌面端更新方向-局部更新方案.md` 的 **P3**）。
> 只讲**怎么用、怎么撤、边界在哪**；语义细节在 `electron/flags.js` 的头注释里。

## 一句话

**代码一次发到齐，功能用开关控制算不算数。** 出事**秒关**，不用发版、不用热更、**断网也生效**。

四条腿的分工（越往下越安全，也越"慢"）：

| 手段 | 换掉什么 | 生效速度 |
|---|---|---|
| A 整包 | Electron 运行时 / 主进程 / 原生依赖 | 退应用 → 装 → 重启（约 1 分钟） |
| B 热更 | 前端页面（`dist/**`） | 点一下 → 重启 2 秒 |
| C 热更 | 账目口径（`electron/commands` 那棵子树） | 点一下 → 重启 2 秒 |
| **开关** | **"这段代码算不算数"** | **立刻（改文件即可，不用重启）** |

## 四层优先级（核心语义，改之前先读三遍）

```
① 服务端下发 "off"   ← 最高
② 本机 flags.json
③ 服务端下发 "on"    ← 只是"建议打开"，本机可以否决
④ 出厂默认（electron/flags.js 里的 FLAG_DEFS）
```

一句话：**服务端能秒关一切，但不能替店里打开；本机自己说了算，除了"关"。**
这么定是因为**"关"永远是安全方向，"开"永远有风险** —— 把"开"的权限交给远端，等于把风险方向也交出去。

## 怎么秒关一个功能

**只关这一台**（马上生效，不需要重启、不需要网络）：

```powershell
# 在 %APPDATA%\fishing-inventory\flags.json 里写：
{ "stockTransfer": false }
```

**关全部门店**（含中心库服务器）：把下面这个文件放到生产机的 `/opt/inventory-cloud/updates/flags.json`
（线上地址就是 `https://sync.junchengzn.com/updates/flags.json`）：

```
{ "flags": { "stockTransfer": false } }
```

> ⚠️ **必须是 `/updates/` 这个前缀**：`sync.junchengzn.com` 反代给 inventory-cloud，
> 只有 `/updates/*` 是现成的静态托管（`/flags/` 会 404）。好处是**零服务端代码改动、不用重启生产**。

各机器每 6 小时来取一次（启动后 22 秒也会取一次），**取到就落盘** —— 所以之后即使断网、或那个地址删了，**"关"仍然继续生效**。

> ⚠️ 这个地址目前**还不存在**（返回 404）。真机验证过：404 时客户端只是"没有新的远端意见"，
> **现状一点不变**，不会因为拉不到就把开关放开。

**界面操作**：「设置 → 功能开关」每行可以直接开/关/"恢复默认"，并显示**当前值 + 来源**（
来源就是上面四层里的哪一层）—— 这样"为什么这行改不动"一眼可见。

**恢复**：删掉 `flags.json`（或点"恢复默认"）。恢复默认后**不会留一个空文件** ——
"这台机器有没有本机覆盖"要一眼看得出来。

## 怎么新增一个开关（三步）

1. `electron/flags.js` 的 `FLAG_DEFS` 加一行：`myFlag: { def: false, desc: '人话说明' }`
2. 在**执行点**加检查（不是只在界面上藏起来 —— 藏 UI 不等于关了，直接调接口照样能写库）：
   ```js
   import * as flags from '../flags.js'
   if (!flags.isEnabled('myFlag')) throw new Error('「XXX」当前已关闭（功能开关）')
   ```
3. 加断言。**后端断言会强制两件事**，缺一个就红：
   - 登记表里每个开关都**真的有调用点**（否则它只是装饰品）
   - 代码里用到的每个名字**都在登记表里**（否则 `isEnabled` 恒为 false = 功能被意外关掉）

## 边界（逐条都是验过的，不是写在文档里就算）

| 边界 | 怎么验的 | 结果 |
|---|---|---|
| 关掉时必须**真的拦住**，且连数据库都不碰 | 用"一碰就炸"的假库当探针调 `transferStock`/`buildBriefing` | ✅ 断言 |
| **不用重启**就生效（这才是"秒"） | 应用运行中放/删 `flags.json`，同一进程立刻变 | ✅ 断言 + **真机** |
| 手改文件也生效（不是只在内存里） | 按 (mtime, size) 指纹热读，断言逐条过 | ✅ 断言 + **真机** |
| 坏文件 / 半截 JSON | 按**出厂默认**继续跑（**不是**把所有功能关掉 —— 那才是事故） | ✅ 断言 |
| 未登记的开关名 | 一律**关**（fail-closed），并在状态里列出来 | ✅ 断言 |
| 名字打错 | **不生效**，但会被 `unknownLocal` 报出来（防"以为关了其实没关"） | ✅ 断言 |
| 服务端"关"压过本机"开" | 表驱动 9 种组合逐个断言 | ✅ 断言 + **真机** |
| 本机"关"能否决服务端"开" | 同上 | ✅ 断言 |
| 下发 404 / 不是 JSON / 网络不通 | 现状不变、不抛异常 | ✅ 断言 + **真机（404）** |
| dataDir 不存在 / 未初始化 | 按出厂默认，状态照样可读；`setLocalFlag` 明确拒绝 | ✅ 断言 |
| 文件写入 | 原子替换、不留 `.tmp`、只写登记的键、0600 | ✅ 断言 |
| 中心库服务器也认开关 | `start-central.mjs` 里 `initFlags(dataDir)` + 断言盯着 | ✅ 断言（**部署后才真正生效**） |

后端断言全绿：`npm run check:assertions`（这一版是 **752** 项，其中开关相关的 43 项）。

## 诚实边界（这一版没做的）

1. **开关是"每台机器各自生效"的**。桌面端改本机文件只影响这台；中心库服务器那份由**它自己的**
   `flags.json`（在服务器 `/opt/inventory-app/data/`）与**同一份远端下发**决定。
   所以关一个功能时，中心库模式下要确认服务端那边也关了 —— 最省事的办法是用**远端下发**（一处生效全网）。
2. **远端下发是静态 JSON，不是接口**：没有鉴权、没有签名。能改那个文件的人就能关/开功能
   （能"开"的只有第 ③ 层，而本机可以否决它 —— 这是当初这么设计的原因之一）。
3. **"开"回不来就靠删文件**：远端只能"关"，想把某个开关**重新打开**得改本机文件或改远端那行为 `true`
   （第 ③ 层），再等各机器来取。
4. **出厂默认改了要发版**（`FLAG_DEFS` 在代码里）。这是有意的：新装的机器不该带着一个没验过的功能默认打开。
