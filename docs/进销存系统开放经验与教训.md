## 二、做对了的事（值得保持的决策）

1. **批次级库存 + 金额按分存（整数）**——inventory_batches 每批独立批次号/成本/货位；全程无浮点金额。周掌柜（16年零售）评价：比很多付费软件规矩。
2. **原子事务**——盘点/多商品开单任一行失败整单回滚，不留半截烂账。
3. **手机版复用桌面版命令层**——两条产品线同一套 electron/commands/ 口径，统计不漂移。
4. **数据目录硬编码 appData/fishing-inventory**——品牌改名/换 appId 时用户数据不丢。
5. **更新源 ASCII 文件名**——inventory-system-setup-x.y.z.exe，避开中文 URL 编码坑。
6. **密码派生密钥（PBKDF2）多设备互通**——所有设备输同一密码→同一密钥→互解，服务器只存盐。
7. **驾驶舱 src/ 模块化构建**——build.js 拼装 + 语法自检 + 占位符残留检查。
8. **负库存默认拦截 + 强制出库留痕**——库存不足返回差多少；强行出库记「负库存-日期」批次提醒补录。

## 三、失败与错误记录（重点，别再踩）

### 3.1 打包与发布类

**❌ dist.cjs 选包 bug（静默装错包）**
- `find(f => f.includes("Setup " + version))` 在复用的临时目录里命中**上次构建的旧品牌包**（Unicode 排序「渔」U+6E14 < 「通」U+901A，旧包排前）。
- 后果：静默安装了旧渔具品牌包，用户看到"内容是通用系统、名字图标是渔具"。
- **修法**：按修改时间取最新（sort by mtimeMs）。**教训**：复用临时目录时 find 不能只按文件名匹配，要按时间戳。

**❌ 0.1.0 发布时更新源是占位符**
- package.json publish.url = `https://your-bucket.cos.ap-guangzhou.myqcloud.com/updates/`（模板默认值没改）。
- 后果：所有 0.1.0 安装检查更新 → 请求无效 URL → 失败被 updater.js catch 静默吞掉 → 显示"已是最新"。
- **教训**：发布前必须验证 publish.url 真实可达；检查更新失败**不能静默显示成功**（要显示"检查失败，请检查网络"）。

**❌ appId 变更导致自动更新断链**
- 渔具版 appId=com.adu.fishing-inventory → 通用版 com.inventory.system。
- electron-updater 按 appId 区分，旧安装**永远检测不到**新产品的更新。
- **教训**：换 appId = 放弃存量用户的自动更新通道，必须手动重装一次。品牌改造前要评估这个代价。

### 3.2 数据正确性类

**❌ 负库存批次把售价写进成本价（周掌柜审计抓出）**
- allowNoStock 强制出库时：`cost_price: sellingPrice ?? 0`——售价直接进成本账。
- 后果：这笔毛利虚高（甚至离谱），月底对账对不上。
- **修法**：成本 = 最近一次有成本的出库流水 → 回退商品档案进价 → 都没有记 0 并挂「待补成本」。流水 unit_price 同口径。
- **教训**：实现"强行出库"这类兜底功能时，**记账口径必须与正常路径一致**，否则兜底变漏洞。

**❌ 手机版加密大库静默降级为明文**
- `btoa(String.fromCharCode(...out))` 展开大数组在 ~50万元素爆 RangeError → catch 吞掉返回**明文**上传。
- 用户设了云同步密码，云端存的却是明文，无任何警告。
- **修法**：分块 base64（32KB 块）+ 加密失败必须抛错（宁可不上传也不传明文）。
- **教训**：任何"加密失败就降级"的设计都是数据安全漏洞；JS 大数组展开是经典坑，用分块。

**❌ PBKDF2 仅 1 万次迭代**
- 弱于 OWASP 2023 建议（≥60 万）。云端被拖库时弱密码可离线爆破。
- **修法**：ENC2 新格式（60万次）+ ENC1 旧密文兼容解密（升级不丢数据）。
- **教训**：加密参数要跟 OWASP 标准；升级加密参数必须做**旧密文兼容**，否则历史数据解不开。

### 3.3 架构与流程类

**❌ 直接改产物而非源码（驾驶舱）**
- 驾驶舱有 src/ + build.js 构建体系，一开始直接改 plugin-host.js（构建产物）——改动会被下次 build 覆盖，被用户纠偏。
- **教训**：动手前先摸清项目的**构建体系**（有没有 src/、build 脚本、测试），改源码层。

**❌ 数据分析缺口（业务视角缺失）**
- 早期只做了低库存/临期/支付拆分，**没做沉睡资金**——周掌柜指出"个体户压死的不是库存不够，是钱变成不动的货"。
- **教训**：功能清单按**老板视角的痛点**排（防呆/省人/呆滞预警/效期/多仓/财务），不是按技术视角排。

**❌ 驾驶舱 6 卡不含库存数据（闭环假象）**
- config.json 里配了 inventory 数据源，但 buildOverview 根本不读它——看起来"数据源已配置"，实际是摆设。
- **教训**：配置了 ≠ 生效。闭环验证要**端到端实测**（插一条数据→看卡片变化），不能看配置就认为通了。

**❌ test-backend summary 断言漂移**
- 种子数据多轮改动后断言没同步（sku 12 vs 56、outQty 18 vs 4...），1/184 长期失败。
- **教训**：种子改动必须同步断言；漂移的失败测试要标记 known-issue 并排期修，不能放任。

**❌ 账号密码公告错误**
- 公告里写密码 jczn1212，但服务器账号真实密码不是它 → 其他电脑登录失败。
- **修法**：服务器重置密码为公告密码（注意：本机 keyK 失效需重新登录，云端旧密文作废）。
- **教训**：发团队账号密码前**先用 API 实测一遍登录**；改密码要评估已加密数据的影响。

**❌ localStorage 状态标记残留**
- 游客模式标记（fi-cloud-guest）测试后残留，导致已配对用户重启仍弹登录门/按游客处理。
- **教训**：客户端状态标记要有清理时机（登录成功/配对成功时强制清除）。

### 3.4 基础设施类

**❌ /opt/ai-server 属 root，scp 静默失败**
- scp 权限不足 exit=1，输出被吞，**误以为部署成功**，服务器跑的还是旧代码。
- **修法**：scp 到 /tmp → sudo mv → systemctl restart。部署后必须验证产物（grep 新代码标记）。

**❌ pm2 restart all 误伤**
- 想重启 ai-server（systemd），执行了 pm2 restart all → 重启了 inventory-cloud，ai-server 没动。
- **教训**：重启前确认服务的**进程管理器**（pm2 / systemd / nohup）和**服务名**。inventory-cloud 走 pm2，ai-gateway 走 systemd。

### 3.5 已知妥协（记录在案，非 bug）

- **HTTP 明文传输**：云同步走 http:// 无 TLS。数据内容已加密，但密码本身明文传。根治需域名+证书。已在手机版加警示条。
- **营收摘要明文落库**：/api/store/report 存明文（view 页服务端渲染无法客户端解密，且 view 已有密码保护）。
- **双代码库漂移**：桌面版与 D:\通用进销存 08-17 快照后各自演进，需明确唯一主线。
- **拍照识别不可用**：ai-gateway 未配豆包 VISION_KEY/MODEL/URL，等 key。

## 四、发布流程 SOP（照着做）

1. 改 package.json version（**每次必须递增**，否则存量用户永远"已是最新"）
2. 打包：`node scripts/dist.cjs`（产物在 release/，临时目录 %TEMP%\fi-release）
3. 部署更新源三件套到 /opt/inventory-cloud/updates/：latest.yml（版本+sha512）+ ASCII 名 exe + blockmap
4. 验证三样：latest.yml 公网可达且版本对 / sha512 与 exe 实际匹配 / 用旧版本实测能检测到（可临时放高版本 yml 验证后恢复）
5. 其他已装新版（0.3.2+）的电脑：设置→检查更新→自动升级。**0.1.0 渔具版必须手动卸载重装**（appId 断链）

## 五、给后来者（人或 Agent）的十条忠告

1. **动手前摸清构建体系**——有 src/ 就改 src/，别改产物；有测试就先跑基线。
2. **发布前验证更新源**——latest.yml 内容、公网可达、sha512 匹配，三样都要验。
3. **兜底功能的记账口径必须与主路径一致**——否则兜底变数据漏洞（负库存成本教训）。
4. **加密失败宁抛错不降级**——静默传明文是最恶劣的失败模式。
5. **闭环验证要端到端**——插一条数据看末端变化，不看配置以为通了。
6. **版本号每次必递增**——否则存量用户永远"已是最新"。
7. **换 appId = 放弃存量自动更新**——评估后再动。
8. **部署后验证产物**——权限坑（root 目录）会让 scp 静默失败；确认进程管理器（pm2/systemd）再重启。
9. **错误不能静默**——catch 吞掉的失败会在远处变成"为什么不好用"。
10. **功能清单按老板痛点排**——防呆/省人/呆滞预警/效期 > 技术上炫的部分。

## 七、周掌柜审计要点摘录（2026-08-28）

- **账实相符 80 分**：批次级库存/原子盘点/负库存拦截/FEFO 效期——底子规矩
- **单据闭环 70 分**：采购应付/销售赊账/退货换货/audit_log 全程留痕——单店够用
- **成本算得清但有一个污染源**：FIFO 摊批次成本是真毛利；负库存售价当成本已修
- **最大空白是呆滞预警**：已补（沉睡资金榜 90/180 两档）
- **明确不做**：多店调拨（等第二家店）、平台库存同步（没电商客户别跟风）、花哨大屏
- **一句话**：账的骨架规矩，欠的三样——负库存成本暗伤（已修）、沉睡资金报表（已补）、应收按单核销（第二档）
