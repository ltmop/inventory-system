# 发布记录（安装包 ↔ 提交 对照表）

> 为什么要有这张表：2026-09-12 手工 bump 出过一个 `1.0.11` 安装包，但那次 bump **没有落进任何提交**
> ——`package.json` 停在 `1.0.10`、`package-lock.json` 停在 `1.0.11`，两边互相矛盾。
> 结果是「这个安装包到底对应哪份代码」查不出来，只能靠时间戳猜。
> 安装包本身在 `.gitignore` 里（`release/`），所以**指纹必须记在这里**，否则换台机器就断了线索。

## 怎么发（三个文件必须一起传）

```
npm run dist
```
产出并自动校验：
- `release/AI智能进销存系统 Setup <版本>.exe`
- `release/AI智能进销存系统 Setup <版本>.exe.blockmap`
- `release/latest.yml` —— **应用内更新读的就是它**，`dist.cjs` 会当场校验它的 `version`
  与 `package.json` 一致、且指向本次构建的那个 exe，不一致直接中止（防自动更新到错版本）

发布 = 把这三个文件传到更新源。只传 `.exe` 的话应用内更新不生效。

**注意**：NSIS 安装包的字节**不可复现**（内嵌构建时间戳等），所以同一份代码重打两次 sha256 会不同。
sha256 用来核对「传上去的包和本地打的是不是同一个」，不是用来标识源码版本的 —— 源码版本看 `提交` 列。

### 发版风控清单（2026-09-14 起照这个走）

1. **版本号唯一**：一个版本号只能有一份字节。bump 之前先确认 `release/` 与 `%TEMP%\fi-release`
   里没有同版本的残留（`Get-ChildItem ... -Filter "*<版本>*"` 应为空）。同版本两份字节 = 永远说不清店里装的是哪份。
2. **构建前工作树必须干净**（本仓库有多个 Agent 共用）：`git status --short` 空 + 已 commit。
   否则打出来的包对应哪份代码说不清。
3. **构建前跑全量门禁**：`npm run build` + 后端 **711** + `check:local` + **`check:central`** + `check:ui`
   + `check:cli` + `check:category` + `check:identity` + `check:update` + **`check:webupdate`** + vitest。
   `check:web` 的**线上段在发布前必然红**（它断言"线上==本版本"），发布前看 A 段即可，发布后要求 26 项全绿。
4. **先 `node scripts/release.mjs --check`**（只检查、不动服务器）：版本递增 / SSH 通 / git 干净。
5. **只跑 `npm run release`** 这一个入口。⚠️ 不要为了"核语法"去跑 `npm run dist` 或
   `node scripts/dist.cjs` —— 它们会覆盖 `release/` 与 `%TEMP%\fi-release` 里的当前版本包（2026-09-14 误操作过一次）。
   核语法用 `node --check <文件>`。
6. **发布后独立复核**，不信脚本自己的话：GET 更新源 `latest.yml` 的 version/sha512/size；
   用 `ssh … sha256sum` 直接读服务器上那份；GET 官网主按钮指向的包（**用 GET，不用 HEAD** —— 这台服务器不支持 HEAD）。
7. **真机走应用自己的更新链路**（`update:check` → `downloadAndInstall`），装完确认
   `User-Agent: inventory-system/<版本>`。用 CDP 探针时**结尾只 `process.exit(0)`，绝不 `browser.close()`**
   —— 后者会把真应用一起关掉（踩过两次）。
8. 最后**更新本文件台账**（版本/提交/打包时间/大小/sha256/状态），并把 `release/` 里那份留作交叉复核的锚点。
9. **（2026-09-15 新增）如果这一版改了前端界面或账目口径**，顺手决定要不要同时发一个热更包：
   `node scripts/build-web-bundle.mjs --check` 自检通过后，改 `public/web-version.txt` 并
   `node scripts/build-web-bundle.mjs`，把 `release/web/` 传到更新源的 `web/` 目录。
   这个包**同时含两层**：页面（`dist/**`，B 通道）+ 口径层（`electron/commands` 那棵子树，C 通道，35 文件 208KB）。
   只想撤掉坏的口径层就用 `--no-code`（客户端把口径层回内置，页面照旧更新）。
   ⚠️ 前端版本号（`public/web-version.txt`，如 `1.1.8.1`）与安装包版本号是**两套**：
   壳版本涨上去（如 1.1.9.0）时，旧热更包会被自动弃用，不需要人工清理。详见
   `docs/运维-桌面端局部更新-Runbook.md`。
   ⚠️ **C 通道换的是主进程里的代码**：能改更新源的人就能在这台机器上执行任意代码（B 通道只影响沙箱页面）。
   发版前务必确认清单是自己构建出来的，不要把别人给的 `latest.json` 直接传上去。
10. **（2026-09-15 新增）新增功能时顺手决定要不要配一个功能开关**（`electron/flags.js` 的 `FLAG_DEFS`）：
    有开关 = 出问题能秒关，不用发版。新增开关后必须跑后端断言 —— 它强制"登记表与调用点一一对应"，
    缺调用点（装饰品）或名字打错（功能被意外关掉）都会红。怎么用见 `docs/运维-功能开关-Runbook.md`。
    ⚠️ 远端下发那份 `updates/flags.json` 是**无鉴权静态文件**：能改它的人能关/开功能（"开"只有建议权，本机可否决）。
    ⚠️ 热更包与开关下发都放在 `/updates/` 前缀下（生产机只有这一个现成的静态托管路由，见 Runbook）。

### 1.1.8 包含什么（owner 反馈「设置里一堆功能不能用」的修复 + 服务端缺口清零）

**根因一条**：中心库模式下桌面端把非本机通道全发给中心库，而中心库上没有这些通道 →
HTTP 404 `unknown channel` → 渲染层 `.catch` 一吞 → 用户看到「点了没反应」。实测共 **62 个**通道。

| owner 报的现象 | 真正的根因 | 修法 |
|---|---|---|
| 收款码无法上传 | `payment:saveQr/deleteQr` 中心库上没有（只有给手机的 `payment:getQr`） | 三者归本机（`payment:record` 是记账，仍走中心库 → 只能逐个点名，不能按前缀一刀切） |
| 手机看店扫码没通过 | ① `server:status` 打到服务器 → 卡片读不到状态、二维码块不渲染；② 二维码用的是 **https 自签证书**地址，微信不给点「继续访问」 | ① `server:*` 归本机；② 看店二维码改用 **http** 地址；③ 卡片上「服务地址」原来显示 `http://ip:<https端口>`（错的）→ 改成真实 http 地址 |
| 官网未链接 | `main.js` 的 `setWindowOpenHandler` 把渲染层 `window.open` **一律拒掉** | 新增单一出口 `openExternalUrl()`（走 `app:openExternal`）；顺带去掉 `HelpPage` 里 `window.location.href` 兜底（会把应用窗口导航到外站，回不来） |
| 意见反馈邮箱没用 | ① `feedback:send` 中心库上没有；② 那个「接收地址」只支持**飞书机器人 https 地址**，填邮箱只会静默存本机，卡片上却没写 | ① 归本机；② 输入框写明「飞书机器人地址（必须 https://…）」+「填邮箱没用」；③ 新增「复制内容」按钮 + 显示客服微信/邮箱（来自 `site:contact` 单一事实源） |
| 关于里仍是「本地单机部署」 | `SettingsPage.tsx` 写死文案 | 改为按中心库配置拼真实模式 |

**缺口清零**（62 → 0，`npm run check:channels` 现在报「当前缺口 0 个」）：
35 个归本机（`LOCAL_ONLY_CHANNELS`），25 个补进服务端（23 个通道 + `ai:analyzePhoto/parseInboundNote` 归本机）。
全部委托 `commands.*`（红线①）；`ai:smartSearch` 的本地兜底口径抽到 `electron/commands/search.js`，桌面端与服务器**共用一份**。

**服务端先部署**（红线⑦顺序）：线上 `/opt/inventory-app/electron/` 补 8 个文件
（备份 `electron.bak-server-20260915-122550.tar.gz`）。体检发现线上是**部分拷贝**：
缺 `commands/clearance.js`、`commands/pricing.js`、`commandApi.js`、`commandRegistry.json`，
且 `commands.js`/`categories.js` 是旧版 → **只传 server.js 会起不来**，所以先算了最小依赖闭包。
**刻意不传 `db.js`**（线上已有知识库助手）→ 避免中心库跑迁移。

### 1.1.1 / 1.1.2 包含什么（owner 反馈「自动提示更新出问题 + 已登录却显示未登录」）

> **哪些提交会让上面这行过期**：`package.json` 的 `build.files` 是 `dist/**`、`electron/**`、`package.json`。
> 只有改动这三处的提交才会改变安装包内容；改 `docs/`、`scripts/` 不影响产物。

> `package.json` 需单独说一句：改它的 `scripts`、`description` 这类元数据**会改变安装包字节**
> （它被打进 asar），但**不影响运行行为**，因此不值得为一个脚本条目重打重发。
> 真正需要重打的是 `dist/**` 或 `electron/**` 的行为变更。
