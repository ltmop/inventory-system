# 发布记录（安装包 ↔ 提交 对照表）

> 为什么要有这张表：2026-09-12 手工 bump 出过一个 `1.0.11` 安装包，但那次 bump **没有落进任何提交**
> ——`package.json` 停在 `1.0.10`、`package-lock.json` 停在 `1.0.11`，两边互相矛盾。
> 结果是「这个安装包到底对应哪份代码」查不出来，只能靠时间戳猜。
> 安装包本身在 `.gitignore` 里（`release/`），所以**指纹必须记在这里**，否则换台机器就断了线索。

## 怎么发（三个文件必须一起传）

```
npm run dist
```
产出并自动校验：
- `release/AI智能进销存系统 Setup <版本>.exe`
- `release/AI智能进销存系统 Setup <版本>.exe.blockmap`
- `release/latest.yml` —— **应用内更新读的就是它**，`dist.cjs` 会当场校验它的 `version`
  与 `package.json` 一致、且指向本次构建的那个 exe，不一致直接中止（防自动更新到错版本）

发布 = 把这三个文件传到更新源。只传 `.exe` 的话应用内更新不生效。

**注意**：NSIS 安装包的字节**不可复现**（内嵌构建时间戳等），所以同一份代码重打两次 sha256 会不同。
sha256 用来核对「传上去的包和本地打的是不是同一个」，不是用来标识源码版本的 —— 源码版本看 `提交` 列。

### 发版风控清单（2026-09-14 起照这个走）

1. **版本号唯一**：一个版本号只能有一份字节。bump 之前先确认 `release/` 与 `%TEMP%\fi-release`
   里没有同版本的残留（`Get-ChildItem ... -Filter "*<版本>*"` 应为空）。同版本两份字节 = 永远说不清店里装的是哪份。
2. **构建前工作树必须干净**（本仓库有多个 Agent 共用）：`git status --short` 空 + 已 commit。
   否则打出来的包对应哪份代码说不清。
3. **构建前跑全量门禁**：`npm run build` + 后端 632 + `check:local` + **`check:central`** + `check:ui`
   + `check:cli` + `check:category` + `check:identity` + `check:update` + vitest。
   `check:web` 的**线上段在发布前必然红**（它断言"线上==本版本"），发布前看 A 段即可，发布后要求 26 项全绿。
4. **先 `node scripts/release.mjs --check`**（只检查、不动服务器）：版本递增 / SSH 通 / git 干净。
5. **只跑 `npm run release`** 这一个入口。⚠️ 不要为了"核语法"去跑 `npm run dist` 或
   `node scripts/dist.cjs` —— 它们会覆盖 `release/` 与 `%TEMP%\fi-release` 里的当前版本包（2026-09-14 误操作过一次）。
   核语法用 `node --check <文件>`。
6. **发布后独立复核**，不信脚本自己的话：GET 更新源 `latest.yml` 的 version/sha512/size；
   用 `ssh … sha256sum` 直接读服务器上那份；GET 官网主按钮指向的包（**用 GET，不用 HEAD** —— 这台服务器不支持 HEAD）。
7. **真机走应用自己的更新链路**（`update:check` → `downloadAndInstall`），装完确认
   `User-Agent: inventory-system/<版本>`。用 CDP 探针时**结尾只 `process.exit(0)`，绝不 `browser.close()`**
   —— 后者会把真应用一起关掉（踩过两次）。
8. 最后**更新本文件台账**（版本/提交/打包时间/大小/sha256/状态），并把 `release/` 里那份留作交叉复核的锚点。

### 1.1.1 / 1.1.2 包含什么（owner 反馈「自动提示更新出问题 + 已登录却显示未登录」）

**根因只有一个**：收银机跑在**中心库模式**（localStorage `fi-central-url=https://app.junchengzn.com`，
运行中的进程有 ESTABLISHED 连接到 43.128.20.39:443），而 `src/lib/api.ts` 在中心库模式下
**把所有通道都发给中心库**；`electron/server.js` 的通道表里**没有** `cloud:` / `update:` 系列（grep 零命中）
→ 一律 `unknown channel` → 渲染层 `.catch` 静默吞掉。两个症状、同一个成因：

| 症状 | 机制 |
|---|---|
| 右上角「未登录」 | `cloud:status` 打到中心库 = 未知通道 → `Layout` 吞掉 → `cloud.paired` 恒 false |
| 自动提示更新出问题 | `update:check` / `update:downloadAndInstall` 同样未知通道 → 设置页「检查失败」/ 点下载毫无反应 |

**1.1.1** 修四处：① `api.ts` 新增 `LOCAL_ONLY_PREFIXES=['cloud:','update:']`，这两类**直连本机 IPC 且绕开离线层**
（离线层给读加 7 天缓存、给写排队 —— 缓存会把一次 `paired:false` 钉死 7 天）；
② `offlineTransport.js` 把这两个前缀加进 `NO_CACHE_PREFIX`；③ `UpdateBanner` 不再静默吞错；
④ `cloud.js` 的 `saveLocalConfig()` 不再静默 return —— 凭证不全时返回 false 并写明原因，
注册/登录两条路径都检查它（修掉「界面显示已登录、本机其实没存」这一族）。

**1.1.2** 修：**顶栏认「已连接中心库」**。真机取证发现：owner 说的「已经登录了」指的是**连上中心库**
（账号页自己就写着「已连接中心库：桌面/手机/网页已同一本账」），而顶栏只认「云账号 / 员工账号」两档，
于是对着一台**正常在用的收银机**说「未登录」。现改为四档：云账号 > 员工身份 > **中心库** > 未登录，
并给身份按钮加悬停说明。

**同时修掉发布脚本自身的一个 bug**（`a65b14a`）：`deployWeb` 把手机版号**硬编码成 `1.1.1`** 并数它的出现次数；
桌面版号一到 `1.1.1`，整页替换必然让计数 `0→7` → 误报「手机版版本号被误改」并中止。
**而中止发生在页面更新之前**，于是 download/ 已换新版、旧版已归档、页面却还指着旧版
→ 实测官网主按钮 `href=/download/general-inventory-setup-1.1.0.exe` **HTTP 404**。
改为从 `fishing-inventory-mobile-X.Y.Z.apk` 文件名解析计数后，用 `--skip-build --web-only` 补齐，按钮恢复 200。

**真机证据**（CDP 连**已安装的应用**，不是浏览器夹具）：
- 1.1.1 上点设置页「检查更新」：`当前 v1.1.1 · 已是最新（9/14 07:17 检查）`（修复前这条路是 `unknown channel`）
- 1.1.2 上顶栏：`… 28 缺货 已连接中心库`（修复前是 `未登录`），同时 `cloud:status` 如实返回 `paired:false`（云账号确实未登）

门禁：`npm run check:local` **39 项**；外加 `api.localChannels.test.ts` 8 项行为级单测
（桩掉 `window.fi` 与 `fetch`，断言运行时真的分路）。本机已装 1.1.2。

- ① `checkForUpdates()` 把异常 catch 成 `{checkedAt}`（没有 version），界面遂把"没有 version"
     当成"没有新版"→ **检查失败被显示成「已是最新」**（比不显示更危险：让人以为查过了）
- ② 设置页渲染条件是 `lastCheckAt && updateMsg`，而失败分支**从不设 lastCheckAt**
     → **消息设了却不显示**（这就是"点了没反应"）

改法：后端返回明确三态 `{ok, hasUpdate, currentVersion, latestVersion, error}`，绝不把失败当最新；
版本改用**数字比较** `cmpVersion`；当前版本改用主进程 `app.getVersion()`（不再用构建时写死的常量）；
界面加显式状态机、成功与失败都设 `lastCheckAt`、状态**始终可见**并显示当前版本号。
另加 `npm run check:update`（16 项断言，含用真实 latest.yml 与本机版本预测按钮会显示什么）。

### ⚠️ 部署顺序（踩过一次的坑，必须记住）

2026-09-13 实测发现：**中心库服务端（app.junchengzn.com）的代码曾长期落后于客户端**。
服务端 `electron/commands/outbound.js` 里 `channel` 命中 0 ——
如果先发客户端、且有人在**中心库模式**下开单，写入要经服务端 `/api/invoke`，
旧服务端的 INSERT 不含 `channel` 列 → 落库时被 DB 触发器兜成「线下」→
**Shopee 单会静默变成线下，而且看起来一切正常**（比报错危险得多）。

所以顺序是：**先更新服务端代码，再发布客户端**。已于 2026-09-13 完成服务端更新：

| 部署的文件 | 备份位置 |
|---|---|
| `electron/channels.js`（新增）、`electron/db.js`、`electron/commands/outbound.js` | `/opt/inventory-app/electron.bak-channel-20260913-103439/` |

部署前逐行 diff 过：24 行"服务端独有"内容全部可归因于旧实现（不含 channel 的签名/INSERT、
以及已被仓库修掉的"建负数量批次"），**没有丢失任何服务端热修**。
部署后 `pm2 inventory-app` online、启动日志 `central db opened, products: 324`、
中央库 `integrity_check: ok` 且数据未变（365 流水 / 客户 0）。

**仍未做**：客户端只发布了包，**两台机器还没实际升级**（需现场）。
不升级的话，同步/离线/渠道能力都不会生效。

> **哪些提交会让上面这行过期**：`package.json` 的 `build.files` 是 `dist/**`、`electron/**`、`package.json`。
> 只有改动这三处的提交才会改变安装包内容；改 `docs/`、`scripts/` 不影响产物。
> 所以记录里的「提交」指**打包时的工作树**对应的提交，之后纯文档/脚本的提交不必重打。
> `package.json` 需单独说一句：改它的 `scripts`、`description` 这类元数据**会改变安装包字节**
> （它被打进 asar），但**不影响运行行为**，因此不值得为一个脚本条目重打重发。
> 真正需要重打的是 `dist/**` 或 `electron/**` 的行为变更。
