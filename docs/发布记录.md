## 怎么发（三个文件必须一起传）

```
npm run dist
```
产出并自动校验：
- `release/AI智能进销存系统 Setup <版本>.exe`
- `release/AI智能进销存系统 Setup <版本>.exe.blockmap`
- `release/latest.yml` —— **应用内更新读的就是它**，`dist.cjs` 会当场校验它的 `version`
  与 `package.json` 一致、且指向本次构建的那个 exe，不一致直接中止（防自动更新到错版本）

发布 = 把这三个文件传到更新源。只传 `.exe` 的话应用内更新不生效。

**注意**：NSIS 安装包的字节**不可复现**（内嵌构建时间戳等），所以同一份代码重打两次 sha256 会不同。
sha256 用来核对「传上去的包和本地打的是不是同一个」，不是用来标识源码版本的 —— 源码版本看 `提交` 列。

### 1.1.0 包含什么（相对 1.0.14）

**商品「子类」从看不见变成看得见 / 搜得到 / 可复用**（`0877e2d`；纯前端，无迁移、不动任何商品数据）。

真缺陷：老板给 **152 个商品**填了 `sub_category`，但库存查询表 **一处都没渲染它**，
关键词搜索也不含它，而入库页/出库页的搜索**反而搜了** → 三处口径不一致。
结果就是"填了看不见、搜不到、下一个还得重打"。

改法：新增 `src/lib/subCategories.ts` 做候选值唯一来源（用得多的排前面、可按品类收敛）；
库存表加「子类」列（12→13 列，**顺带修掉展开行 `colSpan` 既有差一 9→11**）；
关键词搜索与 CSV 导出补子类；高级筛选加子类下拉；建档/编辑表单挂 `datalist` 建议 ——
**仍允许自由输入，150 个真值一个字都不丢**。

> ⚠️ 同时订正一处**我自己的错误判定**：初版诊断据「152 行填了 150 个不同值」把子类判成
> "自由文本污染、应做成受控下拉"。逐条核对原值后确认那是**老板真实的渔具子类词典**
> （伊势尼(粗弯倒刺深) / 丸世 / 纺车轮 / 中通竿 / 筏竿…），全库"用过 ≥2 次"的只有 2 个。
> 受控化会把这 150 个真值压成一张小表、直接丢信息 —— 所以最终做成"**可复用但不受控**"。

证据：`npm run build` ✓；vitest 22 文件 **219 项**；`check:assertions` **632 == 632**（后端断言一条未减）；
新增 `check:identity` **31/0**；新增真机夹具 `check:identity:real` **16/0**
（本次构建 `dist/` + 真实看店服务真库 324 商品：表头渲染出子类列、首屏 50 行 26 行有真值、
搜「粗弯倒刺」收敛到 1 个商品、编辑弹窗 `datalist options=20` 与 SQL 实测"鱼钩 20 个不同值"精确吻合）。

### 1.0.14 包含什么（相对 1.0.13）

**检查更新修复**（`a1f9696`）——owner 反馈「按键没有后端功能、不显示已是最新/有新版」。
查证后：**后端与界面其实都在**（`updater.js`/`main.js` 的 `update:check`、preload 白名单与事件订阅、
设置页按钮与文案、`app-update.yml` 都正常），断点在**失败处理**，两个真缺陷：
- ① `checkForUpdates()` 把异常 catch 成 `{checkedAt}`（没有 version），界面遂把"没有 version"
     当成"没有新版"→ **检查失败被显示成「已是最新」**（比不显示更危险：让人以为查过了）
- ② 设置页渲染条件是 `lastCheckAt && updateMsg`，而失败分支**从不设 lastCheckAt**
     → **消息设了却不显示**（这就是"点了没反应"）

改法：后端返回明确三态 `{ok, hasUpdate, currentVersion, latestVersion, error}`，绝不把失败当最新；
版本改用**数字比较** `cmpVersion`；当前版本改用主进程 `app.getVersion()`（不再用构建时写死的常量）；
界面加显式状态机、成功与失败都设 `lastCheckAt`、状态**始终可见**并显示当前版本号。
另加 `npm run check:update`（16 项断言，含用真实 latest.yml 与本机版本预测按钮会显示什么）。

### ⚠️ 部署顺序（踩过一次的坑，必须记住）

2026-09-13 实测发现：**中心库服务端（app.junchengzn.com）的代码曾长期落后于客户端**。
服务端 `electron/commands/outbound.js` 里 `channel` 命中 0 ——
如果先发客户端、且有人在**中心库模式**下开单，写入要经服务端 `/api/invoke`，
旧服务端的 INSERT 不含 `channel` 列 → 落库时被 DB 触发器兜成「线下」→
**Shopee 单会静默变成线下，而且看起来一切正常**（比报错危险得多）。

所以顺序是：**先更新服务端代码，再发布客户端**。已于 2026-09-13 完成服务端更新：

| 部署的文件 | 备份位置 |
|---|---|
| `electron/channels.js`（新增）、`electron/db.js`、`electron/commands/outbound.js` | `/opt/inventory-app/electron.bak-channel-20260913-103439/` |

部署前逐行 diff 过：24 行"服务端独有"内容全部可归因于旧实现（不含 channel 的签名/INSERT、
以及已被仓库修掉的"建负数量批次"），**没有丢失任何服务端热修**。
部署后 `pm2 inventory-app` online、启动日志 `central db opened, products: 324`、
中央库 `integrity_check: ok` 且数据未变（365 流水 / 客户 0）。

**仍未做**：客户端只发布了包，**两台机器还没实际升级**（需现场）。
不升级的话，同步/离线/渠道能力都不会生效。

> **哪些提交会让上面这行过期**：`package.json` 的 `build.files` 是 `dist/**`、`electron/**`、`package.json`。
> 只有改动这三处的提交才会改变安装包内容；改 `docs/`、`scripts/` 不影响产物。
> 所以记录里的「提交」指**打包时的工作树**对应的提交，之后纯文档/脚本的提交不必重打。
> `package.json` 需单独说一句：改它的 `scripts`、`description` 这类元数据**会改变安装包字节**
> （它被打进 asar），但**不影响运行行为**，因此不值得为一个脚本条目重打重发。
> 真正需要重打的是 `dist/**` 或 `electron/**` 的行为变更。
