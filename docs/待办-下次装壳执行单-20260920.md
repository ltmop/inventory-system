### 1.2 建议一并做（等你一句话我就提交，只在这个壳版本里生效）

**`electron/preload.cjs`：把中心库配置的"补齐"改成"对齐"**

现状（`preload.cjs:12-15`）——只在 localStorage **没有**该键时才用 `central.json` 补齐：

```js
const cfg = ipcRenderer.sendSync('cloud:centralSync') || {}
if (cfg.url && cfg.token && !localStorage.getItem('fi-central-url')) {
  localStorage.setItem('fi-central-url', cfg.url)
  localStorage.setItem('fi-central-token', cfg.token)
}
```

建议改成（main 的 `central.json` 是单一事实源，不一致就以它为准；它非空才覆盖）：

```js
const cfg = ipcRenderer.sendSync('cloud:centralSync') || {}
if (cfg.url && cfg.token) {
  try {
    if (localStorage.getItem('fi-central-url') !== cfg.url ||
        localStorage.getItem('fi-central-token') !== cfg.token) {
      localStorage.setItem('fi-central-url', cfg.url)
      localStorage.setItem('fi-central-token', cfg.token)
    }
  } catch { /* 隐私模式写不进：本次会话按 localStorage 里已有的走 */ }
}
```

| | |
|---|---|
| **好处** | 下次再轮换中心库令牌（或改中心库地址），**各设备只要重启即可自动对齐**，不用人工粘贴、也不用我去改 LevelDB（2026-09-20 那次轮换就是被这条守卫挡住的，见 Runbook §5.3②） |
| **风险** | 改变了启动时"谁说了算"的优先级：从 localStorage 优先变成 `central.json` 优先 |
| **要测的 3 个场景** | ① 两边一致 → 不写（无副作用）② `central.json` 新、localStorage 旧 → 覆盖成新 ③ `central.json` 空（未配中心库）→ **什么都不做**，不能把用户本地配好的配置清掉 |
| **配套断言** | 加"cfg 非空才覆盖"与"两边一致不写"两条静态断言，防止以后被改回单向守卫 |

### 1.3 【不必须等装壳】热更就能修的一个真 bug（今天探活发现）

`electron/commands/analytics.js` 的 `analyticsTop` 引用了 **products 表不存在的列 `p.name`**：

| 行 | 现状 | 后果 |
|---|---|---|
| 64 | `SELECT … p.name, p.brand, … FROM transactions t JOIN products p …` | **抛错** `no such column: p.name` → `/api/analytics/top` 实测返回 **400** |
| 68 | `try { … SELECT id, name, brand … } catch { lookup = [] }` | 作者其实**猜到 name 可能不存在**，这里包了 try/catch；但结果永远是空 → 第 86 行 `name: m?.name ?? '未知商品'` → **所有商品显示「未知商品」** |

- 正确性依据：`products` 表（`electron/db.js:44-66`）**没有 name 列**，只有 `brand/model/sku_code`；
  全仓扫描确认这两行是**唯一**的商品 name 引用（其它 `s.name` 是 `suppliers.name`，有效列）。
- 修法（3 行）：第 64 行去掉 `p.name`；第 68 行改成 `SELECT id, brand, model, sku_code FROM products`（不再需要 try/catch）；
  第 86 行按全仓惯例拼名字：`[m?.brand, m?.model].filter(Boolean).join(' ') || m?.sku_code || '未知商品'`。
- **影响面（2026-09-20 实测）**：中心库 `/api/analytics/top?n=5` → **HTTP 400** `no such column: p.name`；
  同一批里 `/api/analytics/trend` 正常（200），所以**只有 top 这一条坏**。
  受影响的调用方：`scripts/inv-cli.mjs:123`（CLI 的 top）、`analytics:top` invoke 通道，
  以及**三份对外文档把它写成交付接口**（`docs/命令接口-接口文档.md` / `docs/进销存数据分析接口.md` /
  `docs/进销存系统Agent接入指南.md`）—— 即"文档承诺了、调用会 400"。
  桌面端界面与手机端**不受影响**（全仓 grep 确认没有任何渲染层代码调 `analytics:top`）。
- **覆盖缺口**：835 条断言里**没有一条**打这个函数 → 所以它上线后才靠人工探活发现。
  修的时候必须**补一条断言**（用真实 schema 跑一次 `analyticsTop`，别只 grep 源码）。
- **它不用等装壳**：`commands/analytics.js` 在热更 C 通道闭包内 → 可以单独发一版热更（1.1.10.4）就修好。
  **建议**：既然要发壳，一起带上最省事；但如果你想马上能用 `/api/analytics/top`，我先单独发热更。

## 2. 版本号两处同改（最容易漏的一条）

| 文件 | 从 | 到 |
|---|---|---|
| `package.json` 的 `version` | `1.1.10` | `1.1.11` |
| `public/web-version.txt` | `1.1.10.3` | `1.1.11.0` |

**为什么第二处也要改**：`electron/webUpdate.js:338` 的判据是
「热更包 `webVersion` ≤ 内置版本 → 弃用该热更包」。
内置版本提到 `1.1.11.0`（> `1.1.10.3`）后，老热更包自动作废，
用户装上新壳看到的是**新壳自带的前端**，不会出现"新壳 + 旧热更包"的半新半旧状态。
