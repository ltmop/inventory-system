# 渔具库存系统 AI Agent 设计文档

> 版本：v1.0 · 2026-07-29
> 前提：系统为 Electron + 本地 SQLite（node:sqlite），买断制，用户不懂技术

---

## 1. 产品定位：AI 长什么样

**不是聊天机器人，是藏在流程里的隐形 Copilot。**

用户（渔具店老板）不会打开一个对话框跟 AI 聊天。AI 的正确形态是：

| 场景 | 用户看到的 | AI 在背后做的 |
|---|---|---|
| 打烊 | 仪表盘弹出"今日一句话日报" | 汇总流水 → 生成人话小结 |
| 找货 | 搜索框里直接打"赤刃还有几条" | 自然语言 → 查库 → 一句话回答 |
| 入库 | 拍一张送货单照片 | 多模态识别 → 生成入库草稿，人只点确认 |
| 补货 | 开机提醒"YGK 只剩 3 卷，上周卖了 8 卷，建议补 20 卷" | 结合销量算建议补货量 |

原则：**AI 给草稿，人做确认**。任何写操作（入库/出库）都必须人工点确认才落库。

## 2. Agent 类型：工具调用型单 Agent（Function-Calling）

不搞多 Agent 编排，单机店用不上。架构是经典的**单 Agent + 本地工具集**：

```
用户输入（文字/照片）
   ↓
渲染进程 AiPanel（UI 极简：一个输入框 + 回答卡片）
   ↓ IPC: ai:chat
主进程 electron/ai.js
   ├─ 组装 system prompt（当前日期、店铺上下文、工具说明）
   ├─ 调 Kimi API（OpenAI 兼容接口，function calling）
   ├─ 模型返回 tool_call → 本地执行对应工具（查 SQLite）
   ├─ 工具结果回喂模型 → 生成最终回答
   ↓
渲染进程展示（回答 + 数据来源明细 + [确认执行]按钮（写操作时））
```

**关键认知：让 AI"更懂你"不靠训练，靠工具。** 你的商品、批次、流水都在本地 SQLite，AI 通过工具实时查，永远是最新数据，且数据不出本机——发给云端的只有问题文本和查询结果摘要。

## 3. 模型与成本：BYOK（用户自带 Key）

| 项 | 决策 | 理由 |
|---|---|---|
| 首选模型 | Kimi（月之暗面）`kimi-k2` / `moonshot-v1-8k` | OpenAI 兼容接口、中文好、支持 function calling 和多模态 |
| 接口地址 | `https://api.moonshot.cn/v1/chat/completions` | 标准 OpenAI 协议，几十行代码接入 |
| 付费方式 | **BYOK**：设置页填用户自己的 API Key | 买断制不能有订阅成本转嫁；Key 申请一分钟，月费几块钱 |
| 单次成本 | 一次问答 ≈ 1-2K tokens ≈ ¥0.01-0.03 | 一天问 20 次，一个月不到 ¥20 |
| 离线备选 | Ollama + Qwen2.5-7B（后期） | 完全离线零费用，代价是下载 4GB+ 模型、吃电脑配置 |
| Key 存储 | Electron `safeStorage` 加密后写本地文件 | 不明文落盘 |

**降级铁律：没填 Key / 没网络 / Key 失效 → 所有 AI 入口自动隐藏，核心进销存功能零影响。**

## 4. 本地工具集（Agent 的"手"）

### 只读工具（直接执行，无需确认）

| 工具名 | 入参 | 做什么 |
|---|---|---|
| `query_product` | 关键词（名称/品牌/SKU/条码） | 模糊查商品，返回卡片信息 |
| `stock_of` | 商品 ID | 当前总库存 + 分批次明细 |
| `daily_summary` | 日期（默认今天） | 营业额/毛利/件数/出库明细 |
| `top_products` | 天数 N | 近 N 天销量/毛利排行 |
| `low_stock_list` | 阈值（默认 5） | 低库存清单 + 近 30 天销量 → 建议补货量 |
| `slow_moving_list` | 天数（默认 90） | 滞销品清单 |

### 写入工具（只产草稿，必须人工确认卡确认后才调已有 commands 落库）

| 工具名 | 入参 | 做什么 |
|---|---|---|
| `draft_inbound` | 商品、数量、进价 | 生成入库草稿 → 用户确认 → 走 `inbound:create` |
| `draft_outbound` | 商品、数量、售价 | 生成出库草稿 → 用户确认 → 走 `outbound:confirm`（FIFO 逻辑复用，不另写） |

写工具**不直接碰数据库**，只生成结构化草稿传给 UI，确认后复用现有 IPC 命令——FIFO、事务、校验逻辑一处不变。

## 5. System Prompt 设计要点

```
你是渔具店的库存助手。规则：
1. 说人话，禁止术语：不说"FIFO/批次/SKU"，说"先来的货先卖/哪次进的货/商品编号"
2. 回答先给结论，再给数字明细
3. 金额单位是"元"，保留两位小数
4. 库存数字必须来自工具查询，禁止凭记忆编造
5. 入库/出库只能生成草稿，结尾必须说"请核对后点确认"
```

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 用户连 API Key 都不会申请 | 设置页放图文引导 + 一键打开申请页；包装成"AI 激活码"说法 |
| 模型瞎编库存数字 | 强制工具调用（tool_choice），prompt 禁编造；UI 上数字都带"来自库存记录"标签 |
| 网络断/额度用完 | 日报退化为纯模板版（不调 LLM 也能出数字）；问答框提示"AI 暂不可用" |
| 送货单识别错 | 识别结果永远是"草稿"，人工逐行核对后才入库 |
| 隐私顾虑 | 设置页明示："数据存在本机，只有您的问题会发给 Kimi" |
