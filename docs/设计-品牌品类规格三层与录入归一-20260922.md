# 设计：品牌 → 品类 → 规格（三层）+ 录入归一方案

> 起因（老板 2026-09-22 原话）：
> 「这个是简单了能不能让大面积客户接受的了，不管是界面还是操作，这个也是核心竞争力…
>  比如一个品牌的产品，规格很多，但却要每一个都录入，而且还得拍照，规格命名格式不同一，
>  照片无法拍摄多张，假设一个品牌是：狼王，下面是子类：有鱼钩，鱼线，鱼竿等等，然后又分规格，
>  我点击了一个狼王的鱼竿的一个商品，商品下面就可以出来很多规格让我选择，现在这样的反而效率慢了，
>  名字不统一。就像一个文件夹一样，一个文件夹里有很多文件夹，这些文件夹里又有很多文件这样子，而且名字是统一的。」

## 一、实测现状（中心库真库只读体检，2026-09-22）

| 检查项 | 数值 | 含义 |
|---|---|---|
| 商品总数 | 223 | 一行 = 一个规格（商品数 == SKU 数） |
| **品牌为空** | **127（57%）** | 品牌被写进了"型号"文本框 |
| 子类为空 | 190（85%） | 三层树的第二层没有数据支撑 |
| 型号为空 | 0 | 因为整条名字都塞在 model 这一个自由文本框里 |
| 条码为空 | 223（100%） | 扫码开单靠临时生成 |

品类分布：鱼钩 63 / 饵料 45 / 鱼线 41 / 其他 29 / 鱼竿 19 / 工具配件 11 / 浮漂 6 / 铅坠 5 / 路亚假饵 2 / 小药 1 / 渔网 1。

**命名混乱的真实样本**（不是推测，是库里原文）：

- 品牌没落字段、只在名字里：`狼王 拔群丸世9号 10PCS`、`老鬼 九一八 2021版经典配方`、`龙王恨  野战蓝鲫`
  ⇒ 所以「狼王」在库里只找到 **2 个**规格（AI 认得出狼王，但字段没写进去）
- 同一条规格建了两遍：`1042/1043 狼王 拔群丸世10号 10PCS`、`1047/1048 狼王 技群丸世13号`、
  `1053/1054 DAN 岩太郎1.2号 50m`、`1074/1075 AiShang PE鱼线 2.0号 100m`、`1002/1003`、`1009/1010`、`1028/1029`
- 同一件东西两种写法：`渔聖 王者100M…` vs `渔圣 筏PE线…`
- 分隔与空格不统一：`--`、`（竞技版)`（中英括号混用）、1/2/3 个空格混用
- 名字里带备注：`傲湖（还用太空豆）`、`仓吉 太空豆（蓝色包装）`

## 二、结论（先说清楚什么是对的）

1. **数据模型是对的，不要推翻。** 一行 = 一个规格（SKU），品牌 / 品类 / 型号 三个字段分开放 —— 这是这个行业所有进销存/ERP 的共同做法 ✓。
2. **卡点有两个，都不是界面**：
   - ① **录入时没有约束**：品牌/子类是可空自由文本 → 用户图快就全写进"型号"一格 ✗
   - ② **存量数据没归一**：57% 品牌空、85% 子类空、还有重复行 ✗
3. **树建不起来的根因是标签没贴**：再好的文件夹，抽屉不贴标签也找不到东西。**先归一数据，再谈三层视图**。

## 三、方案（四步，按顺序做，每步都能单独验收）

### 第 1 步：存量归一（一次性，需老板点头 + 先备份）
- 写一个**归一脚本**：解析现有 model 文本 → 拆出 `品牌 / 品类 / 规格`，按规则统一分隔符与空格、统一"渔聖/渔圣"这类同义写法。
- **重复行合并**：同名同规格的多条 → 合并为一条（保留有库存/有流水的，另一条标记停用而不是物理删除 —— 历史流水不能动）。
- 产出**人工复核清单**（CSV）：每行给出"原名 → 建议新名 + 建议品牌/品类"，老板改完再落库。
- 验收指标：品牌填充率 57% → **100%**；子类 ≥95%；同名重复 = **0**。

### 第 2 步：录入即规范（这是"效率"的关键）
- **桌面端**（本线负责）：新建商品 / 批量导入时，
  - 品牌、品类改成**下拉 + 可新增**（不再让人自由输入）；
  - 规格按**品类模板**填（鱼竿→长度/调性；鱼线→号数/长度；鱼钩→号数/包装数），**名字由系统拼**（`品牌 + 品类 + 规格`），用户不手写名字；
  - **批量建一族规格**：填一次品牌+品类+公共属性，粘一列规格（每行一个）→ 一次建出 N 个商品（现在是一个一个录入 ✗）。
- **手机端**（手机线负责，界面同上一套规则）：同样的下拉与模板。
- 验收指标：新建一个规格 ≤ 3 次点击；自由文本名字的入口彻底关掉。

### 第 3 步：三层树视图
- 库存页现在已有 **品牌 → 规格** 两级（`BrandGroupList`，2026-09-20 老板要求）。
- 扩成 **品牌 → 品类 → 规格**（就是老板说的"文件夹里还有文件夹"）：第一层品牌卡片，点进去看该品牌的品类，再点进去看规格与数量。
- 桌面端本线负责；手机端手机线负责，**同一套分组规则**（按 brand + category 分组，规则写在后端，两边都别自己算）。

### 第 4 步：多张照片（需动数据库，放最后）
- 现在 `products.photo_path` 只能存**一张** ✗，老板要"拍多张"。
- 方案：新增 `product_photos(product_id, path, sort, created_at)` 表（老字段保留兼容），详情页支持相册式多图。
- 这张表属于**共享层**（桌面与手机都要用），先由本线建表与命令，两端再各做界面。

## 四、不做的事（避免过度设计）

- ❌ 不引入"规格组/变体"新实体：现有 `品牌 + 品类 + 一行商品` 已经够表达，加一层新概念只会让两边更难对齐。
- ❌ 不动既有流水与批次：归一脚本只改商品主表的名字与品牌/品类字段，重复行用"停用"而不是删除。

## 六、给手机线的接口约定（免得两边各做一套）

- 分组一律用后端返回的 `brand + category`，前端不自己拼。
- 命名一律由后端 `productName()`（品牌 + 品类 + 规格）产出，前端不自己拼字符串。
- 多图读取统一走 `photo:list(productId)`（第 4 步产出），单图老字段继续返回，兼容老版本。
