# 桌面端更新方向：从「全量替换」改成「分层局部更新」

> 2026-09-15 整理。**本文只给方向与方案，没有改任何代码、没有动线上。**
> 所有"现状"都是当场核准的（命令与文件位置写在文里，可复算）。

## 〇、先纠正一个前提：这条路上你已经走了一半

「每次都全量更新」这个感受，只在**其中一层**成立。四层里三层已经是局部/自动的：

| 层 | 现状 | 证据（可复算） |
|---|---|---|
| **下载** | ✅ **已经是差分**，不是整包 | electron-updater + `.blockmap`。实测 1.1.4→1.1.6 是差分下载：**57.3 秒、进度 1→100%**，落盘文件与官方包 sha512 逐字节一致 |
| **安装/替换** | ❌ **全量**（这就是"全量"的真正来源） | NSIS 只能装**完整且签名一致**的包 → 必须退应用 → 装 → 重启（收银机停 ~1 分钟） |
| **数据库结构** | ✅ **已经自动跟得上** | `electron/db.js` 的 `runMigrations` + `addCol`：每次启动自查缺哪列就补哪列（幂等 DDL 重放）。新代码要的新列，老库自动长出来 |
| **手机 C 线** | ✅ **已经做了网页层热更** | 你们自己的手机线：逐文件 sha256 差异下载 + 切 WebView 资源根 + 心跳转正 + 版本回退。实测"安装包 23 文件 487KB → 手机只下 2 个文件 44.4KB" |

**所以真正的缺口只有一个**：桌面端的**安装/替换**层还是整包。而这一层能不能局部化，取决于"改的东西在不在业务层里"。

## 一、关键数字：业务层只占安装包的 11%

| 组成 | 体积 | 更新频率 |
|---|---|---|
| `dist/`（前端：页面/样式/图标/壁纸） | **15.3 MB** | 高（每次修 UI/文案/交互） |
| `electron/`（主进程 + 命令层，纯 JS） | **1.1 MB** | 中（口径/通道/同步逻辑） |
| `node_modules/`（原生依赖等） | 706.7 MB（其中语音模型 21.9 MB） | 极低（几乎不变） |
| **安装包（NSIS，含 Electron 运行时）** | **124.7 MB** | — |

**业务层 = dist + electron ≈ 16.4 MB ≈ 安装包的 11%。**
剩下 89% 是 Electron 运行时和原生依赖 —— 它们**几乎从不变**，却每次都被"退应用 + 整包替换 + 重启"地搬一遍。

这就是"每次只更新局部"在桌面端要动的地方：**把那 11% 单独发、单独换**。

## 二、目标形态：三条通道，各自节奏

| 通道 | 内容 | 频率 | 用户感知 | 风险 | 谁来做 |
|---|---|---|---|---|---|
| **A 壳** | Electron 运行时、原生依赖、`preload.cjs`、主进程 | 低（几月一次） | 退应用 → 装 → 重启（约 1 分钟） | 低（完整签名包） | 现在的 `npm run release` 不变 |
| **B 业务层** | `dist/**`（前端全部） | 高 | **秒级**：下完重载页面即生效 | 中（要校验 + 回退） | 新增 |
| **C 口径层** | `electron/commands/**`（纯 JS、**不 import electron**） | 中 | 下完**重启应用进程**（2 秒，不是重装） | 中 | 新增（可与 B 合并发布） |

**C 通道其实是现成的能力**：`electron/commands/` 不依赖 electron（正因如此我今天才能把它**单独部署到中心库服务器**）。它天然是"可独立替换的口径层"。
⚠️ 但要注意：主进程换文件后**必须重启进程**才生效（Node 没有安全的热重载），所以 C 的体验是"2 秒重启"，不是"秒级"。

## 三、⚠️ 三个必须先解决的前置条件（不解决就动会出事故）

### 1. 最危险：localStorage 可能丢配置 → 收银机静默退回本地模式
前端把**中心库地址 + token** 存在 `localStorage`（`src/lib/api.ts` 的 `fi-central-url` / `fi-central-token`，还有游客标记、局域网令牌）。
热更会把页面路径从 `resources/app.asar/dist/index.html` 换成别的目录 —— **`file://` 页面的存储归属是否跟着变，必须先实测**。一旦变了，收银机就会**静默退回本地模式**（正是《中心库归一 Runbook》里写的那个危险场景：门店以为在看中心库的账，其实在看本机那份旧账）。

**处置（两条，按实测结果选）**
- 先实测：切目录前后 `localStorage.getItem('fi-central-url')` 是否还在（这个测试本身 10 分钟能做完）。
- 无论结果如何，**推荐先做迁移**：把这几个 key 从 localStorage 搬到主进程文件（`dataDir/*.json`）+ 用 IPC 读。
  这个模式**你已经有**：方案A 的 `central-mode.json` 就是"主进程落盘 + 渲染层上报"。搬完之后，前端不再依赖"页面路径"来记住自己是谁。

### 2. 服务端也要跟着切版本（否则桌面新、手机旧）
`electron/main.js` 里：`createInventoryServer({ webRoot: path.join(__dirname, '../dist') })`
—— **手机看店 / 中心库服务端也从 `dist` 提供前端**。
所以热更目录必须**同时**喂给两处：`mainWindow.loadFile(...)` 与 `webRoot`。只改一处 = 桌面看新版、手机看旧版 —— 就是这几轮一直在治的"两个版本并存"。

### 3. 前端→壳的通道兼容（否则重演今天那 62 个通道的静默失败）
热更包如果引用了**当前壳不支持的 IPC 通道**，就会重演"点了没反应"。
→ 热更包必须带 `minShellVersion`，并且发布前用**已有的 `npm run check:channels` 闸门**校验："热更包引用的通道 ⊆ 当前壳支持的通道"。不满足就**拒绝加载**（退回上一版），绝不半可用。

## 四、护栏（缺一个都不上）

1. **逐文件 sha256**：下到 `<版本>.tmp/` → 全部校验通过 → **原子改名**成正式目录；任何失败保留旧目录
2. **转正与回退**：新版本启动后跑自检（版本号正确 + 首页能渲染 + 数据库能打开）→ 通过才写 `web-current.json` 转正；
   否则**下次启动自动退回上一版**（手机线已有 `markHealthy` 心跳模式，照搬）
3. **热更包只装业务层**：`dist/**` + `electron/commands/**`；**绝不含** `node_modules/`、原生依赖、语音模型
4. **用户可见**：更新就绪时明确提示（"新版本已就绪，点这里生效"或下次启动自动生效），不静默替换

## 五、不该做的（诚实三条）

- **不做主进程任意代码的热替换**（你文章里 Sophix/JVM 那类）。Electron 没有安全的热重载机制，而那正是"签名完整包"要防的事。主进程改动就走 A 通道。
- **不为省流量去切 NSIS 包**。签名与完整性是安全边界，不是成本项。
- **不把原生依赖/模型放进热更包**。它们不变，放进来的唯一效果是让每次更新变慢。

## 六、第三条腿：Feature Flag（比热更更安全）

代码**全量发到齐**，功能**用开关控制谁可见**：出事秒关，不用发版。
现成的落法：沿用 `electron/site.js` 那套"**出厂默认 + 本机文件覆盖**"的单一事实源，再加一个服务端下发的开关对象。
优先级高于 C 通道 —— 同样的"秒级回滚"效果，风险却更低。

## 七、优先级与验收指标

| 优先级 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **P0** | localStorage 关键配置迁移（+ 切目录实测） | 不做后面全是雷：一次热更就可能让收银机看错账 |
| **P1** | B 通道：`dist` 热更 + 四道护栏 | 收益最大：UI 修复从"1 分钟停机"变成"秒级" |
| **P2** | C 通道：`electron/commands` 热更（与 B 合并发） | 口径/通道类修复不再走 124MB 整包 |
| **P3** | Feature Flag | 秒级回滚，风险最低的一条腿 |
| 可选 | 两个 6MB 壁纸改成按需下载 | 首装瘦身约 12MB（对"每次更新"无影响，因为差分/逐文件本来就不重复传） |

**验收指标（都可测）**
- 一次纯 UI 修复的**用户可见等待**：现在 ≈60 秒 → 目标 **≤5 秒**
- 每次更新的**下载量**：现在（差分）数 MB → 目标 **<500KB**（逐文件差异，未变资源不传）
- **回退能力**：新版启动自检失败必须自动退回上一版（**现在完全没有这个能力**）

## 八、今天做了什么 / 没做什么

- 做了：核准四层现状（含实测数字）、找出三个前置条件、定通道与护栏、定优先级与验收指标
- **没做**：没有改任何代码、没有动线上、没有改数据结构
- 下一步只需要你点一个头：**从 P0（localStorage 迁移 + 切目录实测）开始**，还是**先做 Feature Flag**（更小、更快见效）
