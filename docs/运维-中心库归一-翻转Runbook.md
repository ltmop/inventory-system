# 中心库归一（P0）翻转 Runbook

> 目的：把门店桌面从「本机数据」切到「云端中心库」，让多台/多地共用同一份账。
> **本文的前提结论全部是实测的**（2026-09-13，阿杜），不是推测。行号随代码变动，以函数名为准。

---

## 0. 先说结论：现在**不能**直接翻，顺序反了会丢数据可见性

翻转的动作本身很简单（填两个字段 + 重启）。**危险不在动作，在于翻完之后门店看到的是哪份数据。**

实测中央库（`/opt/inventory-app/data/data.db`）当前内容：

| 表 | 行数 | 说明 |
|---|---|---|
| transactions | 365 | 入库 333 + 出库 32（优选仓发货 31、店长 1） |
| products | 324 | |
| inventory_batches | 337 | |
| stock_take_items | 303 | |
| **customers** | **0** | 赊账客户完全没接上 |
| **payments** | **0** | 还款/应收完全没接上 |
| expenses / purchase_orders / price_tiers / kits | 0 | |

而门店的真实零售、客户、应收**还在门店本机**。

> ⚠️ **把门店切到中心库 = 门店从此只看得见中心库那份数据。**
> 中心库客户 0、应收 0 → 门店翻完之后**看不到自己的赊账客户和应收款**。
> 这不是"少几个功能"，是账实不符的现场。

**所以正确顺序是：先把门店数据推上中心库并核对账实，再翻转。** 先翻后补 = 现场必乱。

## 1. 现状（已核实，含代码位置）

| 事实 | 证据 |
|---|---|
| 桌面**默认走本地 IPC**，中心库是设置里的 opt-in | `src/lib/api.ts` 的 `rawBackend`：只有 `localStorage` 同时有 `fi-central-url` 与 `fi-central-token` 才连中心库，否则回落 `window.fi`（本地 IPC） |
| 配置存在 **localStorage**，不是配置文件 | `api.ts` 的 `getCentralConfig` / `setCentralConfig`，键名 `fi-central-url` / `fi-central-token` |
| 切换入口是**手动**的，不随登录自动切 | `src/components/CloudLoginGate.tsx`：点「连接中心库」→ 填 URL+token → `setCentralConfig` → `window.location.reload()` |
| 中心库地址 | `https://app.junchengzn.com`（`src/pages/settings/CentralModeCard.tsx` 的默认值） |
| 中心库由 `/api/invoke` 提供服务，与桌面同码 | `electron/server.js` 的 `handleInvoke` |

> 📌 **更正 CHANGELOG**：v1.0.9 那段写的「登录即 `setCentralConfig`（默认切中心库入口）」**不准确**。
> 实测登录与切中心库是两个独立的手动动作，**登录不会**把机器切到中心库。
> 写"登录即切换"会让人以为登录是安全的，从而在没备份的情况下放心登录 —— 属于危险描述，建议改掉。

**另一处补充**：`fi-central-*` 存在 localStorage，意味着
（a）换个 Windows 用户 / 清了浏览器数据，配置就没了，机器会**静默退回本地模式**；
（b）装机时无法由安装包预置默认值 —— 要改默认只能改代码。

## 2. 翻转前必须做的（缺一不可）

1. **备份门店本机库**（这是唯一的原始账，丢了不可重建）
   ```
   # 门店那台机器上执行（客户端先关闭）
   node scripts/server/snapshot-db.mjs --label pre-central-flip
   ```
   该脚本用 `VACUUM INTO` 做在线一致快照，并**自证**（能独立打开、`integrity_check=ok`、
   逐张表行数与源库一致），不一致就 exit 1 并明确告诉你别拿它当退路。
   ⚠️ **不要**用复制粘贴 `.db` 文件的方式备份 **正在使用** 的库：WAL 模式下主库文件
   加上尚未 checkpoint 的 `-wal` 才构成完整状态，只拷 `.db` 会漏掉最近事务。
2. **记录门店本机的账实基线**（翻转后要逐项核对）：
   客户数、应收合计、本月零售笔数、库存总值、各 SKU 数量。
3. **把门店数据推上中心库**（这是目前唯一缺的一步，方式见 §3）。
4. **核对账实相符**：中心库里上述每一项与门店基线一致，才算具备翻转条件。

---

## 3. 把门店数据推上中心库（当前缺口的补齐方式）

三条路，按推荐度排列：

| 方式 | 做法 | 评价 |
|---|---|---|
| **A. 中心库模式直连录入**（推荐） | 先只把**一台**机器切中心库，用它把门店的历史客户/应收录进去，核对无误后再切其他机器 | 最可控，可逐项核对；缺点是人工量 |
| **B. 门店本机 → 导出一份库 → 推到中心库** | 用 `scripts/server/central-data-audit.mjs` 先量缺口，再按 kind 定向补 | 需要一次性搬运脚本；**当前没有**这个脚本（见 §6 未做） |
| **C. 增量同步（sync.junchengzn.com）** | 登录云账号后走 2.0–2.3 按记录同步 | 与中心库**不是同一套**：同步云存的是加密密文，中心库是明文业务库。走它能多端一致，但**不会**自动填充 `app.junchengzn.com` 的库 |

> ⚠️ **别混淆两个"云"**（这是最容易搞错的一点，会让"首单判据"永远为 0）：
> - **中心库** = `app.junchengzn.com` → 台账 line 104 指定的**首单判定唯一权威口**
> - **同步云** = `sync.junchengzn.com` → 多机防覆盖的按记录加密同步
> 两者数据不互通。**首单判据只读中心库。**

## 4. 翻转操作（每台机器一次）

1. 确认 §2 的 4 项都完成。
2. 打开软件 → **设置 → 连接云端中心库**。
3. 地址填 `https://app.junchengzn.com`；token 向 owner 索取（每台机器用同一套地址+token）。
4. 点「保存并连接中心库」→ 软件自动重启（`window.location.reload()`）。
5. 重启后**立刻核对**：客户数、应收合计、今日流水 —— 与 §2 记录的基线一致。
6. 记账软件改名不改账：确认左上角/设置里显示的是「中心库」而不是「主机」。

## 5. 回退（不想要了就退回本地，数据不丢）

清掉两个 localStorage 键即可恢复本地 IPC，**本地库一直没有被改动**：

```
设置 → 连接云端中心库 → 清空地址或 token → 保存
```
（等价于 `setCentralConfig('', '')`；或由 owner 在浏览器控制台执行后 reload。）

**回退的前提**：本地库本身没被写过。所以翻转后如果门店在中心库模式下开了单，
那些单子**只在中心库**，退回本地就看不到它们 —— 回退前必须先把中心库的新单子补回本地。

## 6. 未做 / 需要 owner 拍板的

- **是否把中心库设为默认**：这是**代码改动**（当前默认是本地，`api.ts` 的 `rawBackend` 三档优先级里的第一档要改成无条件优先）。
  按红线「产品线生死/多店由老板拍板」，我**没有**单方面改。要做请 owner 明确授权，并说明对没有中心库配置的存量机器的影响（它们会连不上、必须回退）。
- **一次性搬运脚本（§3 方式 B）**：没写。写了才有"把门店库定向补进中心库"的机械路径，否则只能人工录。
- **翻转本身**：需要门店现场 + owner 授权，我没有执行，也不该由 agent 单方面执行。
- **RTO/第二位置**：见 `docs/运维-备份与恢复-Runbook.md`。
