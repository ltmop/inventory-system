# 中心库归一（P0）翻转 Runbook

> 目的：把门店桌面从「本机数据」切到「云端中心库」，让多台/多地共用同一份账。
> **本文的前提结论全部是实测的**（2026-09-13，阿杜），不是推测。行号随代码变动，以函数名为准。

---

## 0. 先说结论：现在**不能**直接翻，顺序反了会丢数据可见性

翻转的动作本身很简单（填两个字段 + 重启）。**危险不在动作，在于翻完之后门店看到的是哪份数据。**

实测中央库（`/opt/inventory-app/data/data.db`）当前内容：

| 表 | 行数 | 说明 |
|---|---|---|
| transactions | 365 | 入库 333 + 出库 32（优选仓发货 31、店长 1） |
| products | 324 | |
| inventory_batches | 337 | |
| stock_take_items | 303 | |
| **customers** | **0** | 赊账客户完全没接上 |
| **payments** | **0** | 还款/应收完全没接上 |
| expenses / purchase_orders / price_tiers / kits | 0 | |

而门店的真实零售、客户、应收**还在门店本机**。

> ⚠️ **把门店切到中心库 = 门店从此只看得见中心库那份数据。**
> 中心库客户 0、应收 0 → 门店翻完之后**看不到自己的赊账客户和应收款**。
> 这不是"少几个功能"，是账实不符的现场。

**所以正确顺序是：先把门店数据推上中心库并核对账实，再翻转。** 先翻后补 = 现场必乱。

## 1. 现状（已核实，含代码位置）

| 事实 | 证据 |
|---|---|
| 桌面**默认走本地 IPC**，中心库是设置里的 opt-in | `src/lib/api.ts` 的 `rawBackend`：只有 `localStorage` 同时有 `fi-central-url` 与 `fi-central-token` 才连中心库，否则回落 `window.fi`（本地 IPC） |
| 配置存在 **localStorage**，不是配置文件 | `api.ts` 的 `getCentralConfig` / `setCentralConfig`，键名 `fi-central-url` / `fi-central-token` |
| 切换入口**两条**：常规=登录后自动配；紧急=高级设置里手填 | 常规：`AccountPage` → `CloudCard.handleAccount` 登录成功后调 `cloud:centralConfig` 拿地址+token → `setCentralConfig` → reload。紧急：`src/pages/settings/CentralModeCard.tsx`，**只有 `advanced`（设置页「高级设置」打开）时才显示手填框** |
| 中心库地址 | `https://app.junchengzn.com`（`src/pages/settings/CentralModeCard.tsx` 的默认值） |
| 中心库由 `/api/invoke` 提供服务，与桌面同码 | `electron/server.js` 的 `handleInvoke` |
| **中心库模式下主进程会停掉「整库上传」** | `electron/cloud.js` 的 `wholeDbUploadBlocked()`：`syncSnapshot`（云看板）与 `uploadBackup`（每日备份）在中心库模式下直接 return；按记录同步 `syncBusinessData` 也返回"没做"。开关由渲染层上报（`cloud:setCentralMode`）并落盘 `dataDir/central-mode.json` |

> 📌 **更正 CHANGELOG（初版）**：v1.0.9 那段写的「登录即 `setCentralConfig`」当时**不准确**（登录与切中心库是两个独立动作）。
> **2026-09-14 起它变成准确的了**：方案C 把手填 token 收进「高级设置」，登录后自动配中心库成了**常规唯一入口**。
> 但危险描述那半句仍然成立、且更要紧：**登录本身不等于数据安全** ——
> 见下面「§1b 中心库模式 vs 云账号」里那条"整库上传"的说明。

**另一处补充**：`fi-central-*` 存在 localStorage，意味着
（a）换个 Windows 用户 / 清了浏览器数据，配置就没了，机器会**静默退回本地模式**；
（b）装机时无法由安装包预置默认值 —— 要改默认只能改代码。

## 1b. 中心库模式 vs 云账号：两件不同的事（方案A/C，2026-09-14 owner 拍板）

这两个东西经常被当成"要登录两次"，其实分属两层：

| | 中心库模式 | 云账号（`cloud.json`） |
|---|---|---|
| 回答的问题 | **账本放在哪** | **这台机器是谁 + 谁做备份/看板/增量同步** |
| 实现 | `localStorage` 的 `fi-central-url`/`fi-central-token`；`api.ts` 的 `rawBackend` 中心库优先，业务通道全走 HTTP | `dataDir/cloud.json`（userId+uploadToken+viewToken+keyK）；`cloud.js` 的 `getBizSync()` 三道门槛 |
| 连上以后 | 全店共用服务器上那一份 `data.db`，多机天然同账，**不需要同步** | 解锁：按记录增量同步、手机看板整库快照、每日整库备份、换机恢复、以及**自动下发中心库地址**（`/api/cockpit/central-config`） |
| 关系 | 中心库地址本身就是**登录的产物**（登录 → 换令牌 → 领地址） | 云账号没了（`cloud.json` 不存在）也不影响中心库继续用 —— 会出现「中心库连着的，但云账号没登」这种半截状态 |

**方案A（为什么必须拦住整库上传）**：中心库模式下界面上读写的是**服务器那一份**，
本机 `data.db` 不是权威账本、而且越用越旧。而主进程手里有三条会读本机库往云上送的通道。
`needsRestore` 那道保护只对**全新机器**（`settings.fi-onboarded != '1'`）生效 ——
**已经营过一阵的收银机没有保护**，一登录就会拿旧库覆盖云端看板/备份。所以：

- `syncSnapshot()`（→ `/api/snapshot`，喂手机看板）：中心库模式下**不发**
- `uploadBackup()`（→ `/api/backup`，每日备份按日期覆盖）：中心库模式下**不发**
- `syncBusinessData()`（→ `/api/tenant/sync`）：中心库模式下返回 `ok:false`（方向搞反了：本机库此时是旧的那份）

代价如实说：**中心库模式下这台机器不再更新云看板与云备份**。要看板/备份，应由**中心库那一侧**
生成（属于后续工作，不属于本文）。宁可停掉，也不能拿旧库覆盖好数据。

**方案C（一个入口）**：手填 URL+token 不再是常规入口 ——
常规界面只显示「连没连上 / 断开」，没连上时引导去「账号」页登录（登录会自动配好）；
手填框只在设置页**「高级设置」打开时**出现，留给排障与本文的紧急路径。

**守这个决策的闸门**：`npm run check:central`（`scripts/verify-central-mode.mjs`，34 项）。
它**不是 grep 源码**：用 `electron/db.js` 开一个真库、真 import `cloud.js`、桩掉 `fetch` 数请求，
断言"中心库模式下 `/api/snapshot` 与 `/api/backup` 一个字节都没发"，并且**反向断言**本地模式下确实会发
（防止闸门被写成"永远拦住"），外加"重启后仍知道自己是中心库模式"（否则启动 2 秒后那次自动快照会漏网）。

## 2. 翻转前必须做的（缺一不可）

1. **备份门店本机库**（这是唯一的原始账，丢了不可重建）
   ```
   # 门店那台机器上执行（客户端先关闭）
   node scripts/server/snapshot-db.mjs --label pre-central-flip
   ```
   该脚本用 `VACUUM INTO` 做在线一致快照，并**自证**（能独立打开、`integrity_check=ok`、
   逐张表行数与源库一致），不一致就 exit 1 并明确告诉你别拿它当退路。
   ⚠️ **不要**用复制粘贴 `.db` 文件的方式备份 **正在使用** 的库：WAL 模式下主库文件
   加上尚未 checkpoint 的 `-wal` 才构成完整状态，只拷 `.db` 会漏掉最近事务。
2. **记录门店本机的账实基线**（翻转后要逐项核对）：
   客户数、应收合计、本月零售笔数、库存总值、各 SKU 数量。
3. **把门店数据推上中心库**（这是目前唯一缺的一步，方式见 §3）。
4. **核对账实相符**：中心库里上述每一项与门店基线一致，才算具备翻转条件。

## 3. 把门店数据推上中心库（当前缺口的补齐方式）

三条路，按推荐度排列：

| 方式 | 做法 | 评价 |
|---|---|---|
| **A. 门店库 → 中央库 一次性搬运脚本**（推荐，**已就绪**） | 见下方 §3.1 | 可只读预演、可重跑、冲突不覆盖；已用真实中央库副本端到端验证 |
| **B. 中心库模式直连录入** | 先只把**一台**机器切中心库，用它把门店的历史客户/应收录进去，核对无误后再切其他机器 | 只适合补少量数据；人工量大 |
| **C. 增量同步（sync.junchengzn.com）** | 登录云账号后走 2.0–2.3 按记录同步 | 与中心库**不是同一套**：同步云存的是加密密文，中心库是明文业务库。走它能多端一致，但**不会**自动填充 `app.junchengzn.com` 的库 |

### 3.1 搬运脚本用法（`scripts/server/backfill-central-from-local.mjs`）

```bash
# 1) 只读盘点：看清会新增什么、有没有冲突（什么都不改）
node scripts/server/backfill-central-from-local.mjs --src <门店库> --dst <中央库>

# 2) 预演：打印将执行的 INSERT 样例
node scripts/server/backfill-central-from-local.mjs --src <门店库> --dst <中央库> --plan

# 3) 执行（先对中央库做 VACUUM INTO 备份并自证）
node scripts/server/backfill-central-from-local.mjs --src <门店库> --dst <中央库> --apply --yes
```

它的安全设计（对应本场景的失败模式）：

| 机制 | 为什么 |
|---|---|
| 默认只读，执行要 `--apply --yes` | 往生产库写数据，必须两步确认 |
| 写前对**目标库** `VACUUM INTO` 快照 + `integrity_check` 自证，不一致 exit 1 | 退路不可信就不许动手 |
| 按主键逐行分类 **新增 / 冲突 / 已一致**，**只写新增** | 覆盖会静默改掉门店的账 —— 这是最危险的失败模式 |
| 冲突只报告、列出哪些字段不同 | 谁对得人来判断，脚本不替人做决定 |
| 列取两边**交集** | 中央库没有 `guid` 而门店库有，这类不对称自动跳过 |
| 跳过 `settings`/`users`/`idem`/`ai_*`/`audit_log`/`sync_*` | 那些是机器本地状态，不是业务数据 |
| 父子表顺序固定（父在前）、整批一个事务 | 任一失败整体回滚，不留半截数据 |
| 可重跑：第二次执行应报「没有需要新增的行」 | 中断了能直接重来 |

**实测证据**（`node scripts/test-backfill-central.mjs`，19 项断言全过）：
覆盖只读不改数据、分类正确、**冲突不被覆盖**、值正确、幂等重跑、备份自证，
以及端到端的一条：**补进一笔 Shopee 零售后，「首单」判据从 0 变 1** ——
即这个脚本确实能解开 P0，而不只是搬数据。

**用真实中央库副本另跑过一次**（`D:\服务器备份\进销存中央库\central-20260913-1010.db`），
发现 **17 行冲突**（其中 `transactions` 1 行，就是已知的 `id=309` 分歧：
中央库是 `out/¥7.50/现金/店长`，本机是 `in/优选仓发货`）。
**这 17 行必须先人工判定谁对**，再决定要不要搬运 —— 脚本不会替你覆盖。

### 3.2 冲突怎么看、怎么判、怎么落地（三个工具一条链）

```bash
# ① 出对照报告：同 id 但内容不同的行，逐字段并排，带两边 sha256 与判定表
node scripts/server/conflict-report.mjs --src <权威库> --dst <目标库> \
  --labels "本机,中央库" --out 冲突对照.md

# ② 人判：按报告填一份判定 JSON（take=src 取源 / take=dst 取目标）
#    ③ 落地：只改判定文件里明确列出的行，没列的一行不动
node scripts/server/apply-conflicts.mjs --src <权威库> --dst <目标库> --judgments 判定.json           # 预演
node scripts/server/apply-conflicts.mjs --src <权威库> --dst <目标库> --judgments 判定.json --apply --yes
```

为什么把「判」和「改」拆成两步：**覆盖冲突行会静默改掉账**。所以搬运脚本只写「新增」，
冲突一律跳过；要改必须由人显式列出。`apply-conflicts` 的三道护栏：
默认只读；执行前对目标库 `VACUUM INTO` 备份并自证；
**判定里列出的行若当前不再是冲突，直接拒绝执行（exit 2）** —— 防止拿过期判定去改库。

**实测证据**：`node scripts/test-backfill-central.mjs` **29 项断言全过**，含
预演不改数据、按判定改写、备份自证、过期判定被拒且数据未动、`take=dst` 不写库。

### 3.3 ⚠️ 实测发现：中央库不是「旧镜像」，两库是**双向**分叉

2026-09-13 对本机库与中央库副本做了逐行比对：**16 行冲突、0 行新增**。冲突聚成三簇，
其中两簇可以用**账本算术**判定（不靠人猜）：

| 簇 | 行数 | 事实 | 判定 |
|---|---|---|---|
| `inventory_batches` 281/282/283/285/286/290/291 | 7 | 每个批次中央库都比本机多 5。两边**都有**那笔「优选仓发货」出库（流水 id 358/360/362/364/366/368/370 完全相同），但中央库的批次数量没扣 → **中央库与自己的流水账矛盾** | **本机对**（流水净剩 = 本机值） |
| `products` 281~291 | 7 | 本机 `cost_price=0`，中央库 `300`（¥3.00）；而本机**自己的**批次成本与流水 `unit_price` 都是 300 | 倾向**中央库对**（本机 product 与自己的明细矛盾）；⚠ 影响毛利，需 owner 确认 |
| `transactions` id=309 + `inventory_batches` id=1 | 1+1 | 见下 | **必须人判** |

**关键发现**：`transactions.id=309` 是**两张完全不同的真实单据撞了同一个 id** ——
中央库是 `type=out、¥7.50、现金、店长、2026-09-11T21:00:11`（且从 batch 1 扣了 1），
本机是 `type=in、优选仓发货、2026-09-06`。batch 1 的差异（30 vs 29）正是这笔的下游：
**两边都与自己的流水账自洽**，所以不能用算术判。

⇒ **有人直接在中央库侧录过单**。中央库不是纯镜像，两库是双向分叉。
这同时意味着：那笔 ¥7.50 是**真实销售**（有批次扣减、有店长署名），不是脏数据；
但它渠道是「线下」，**不构成 Shopee 首单**。

> ⚠️ **两条不能做的事**：不要为了让账看起来一致就删掉中央库那行（等于抹掉一笔真实销售）；
> 也不要因为「想让首单推进」就把它算成 Shopee。它的渠道已被校正为「线下」。

### 3.4 ⚠️ 搬运的三个必须知道的前提（时点 / 去重 / 不覆盖）

1. **搬运是「时点」操作，不是持续同步。**
   搬完到翻转之间，门店若继续在本机开单，那些单**不会**自动进中央库。
   所以正确节奏是：**停止门店录入 → 备份 → 搬运 → 核对账实 → 立刻翻转**，
   中间不要让门店继续做生意。若做不到，翻转前必须**再跑一次**搬运（脚本可重跑，
   第二次会只搬新增的那部分）。
2. **去重是按 `id` 做的，前提是两库同源。** 两库一旦分叉过，同一笔业务可能在两边
   有**不同 id** —— 那会被当成新行插入，变成重复单。脚本会按业务自然键
   （客户按姓名；流水按 商品+时间+数量）**报警但不拦**，看到「疑似重复」必须人工确认。
3. **不做覆盖。** 冲突行（同 id 不同内容）一律跳过并列出差异字段。
   如果判定「门店版才对」，那需要人工单独处理，脚本故意不提供自动覆盖开关。

> ⚠️ **别混淆两个"云"**（这是最容易搞错的一点，会让"首单判据"永远为 0）：
> - **中心库** = `app.junchengzn.com` → 台账 line 104 指定的**首单判定唯一权威口**
> - **同步云** = `sync.junchengzn.com` → 多机防覆盖的按记录加密同步
> 两者数据不互通。**首单判据只读中心库。**

## 4. 翻转操作（每台机器一次）

1. 确认 §2 的 4 项都完成。
2. **首选**：到「账号」页登录云账号 —— 登录成功后软件会自动向服务器领中心库地址+token 并重启生效
   （`CloudCard.handleAccount` → `cloud:centralConfig`），**不用手填任何东西**。
3. 只有在**登录路走不通**（服务器没返回中心库配置、或要连一个非本账号的中心库）时，才走手填：
   打开 **设置 → 高级设置** → 「云端中心库」卡片里会出现地址/token 输入框 →
   地址填 `https://app.junchengzn.com`，token 向 owner 索取（每台机器用同一套地址+token）。
4. 点「保存并连接」→ 软件自动重启（`window.location.reload()`）。
5. 重启后**立刻核对**：客户数、应收合计、今日流水 —— 与 §2 记录的基线一致。
   同时确认中心库卡片上写着「已连接」，并留意那句「整机备份已暂停」的提醒（见 §1b 方案A）。
6. 记账软件改名不改账：确认左上角/设置里显示的是「中心库」而不是「主机」。

## 5. 回退（不想要了就退回本地，数据不丢）

清掉两个 localStorage 键即可恢复本地 IPC，**本地库一直没有被改动**：

```
设置 → 高级设置 → 云端中心库 → 「断开（回到本机数据）」
```
（走的就是 `setCentralConfig('', '')`；或由 owner 在浏览器控制台执行后 reload。
断开后主进程那侧的整库上传闸门也会跟着放开 —— 渲染层上报 `cloud:setCentralMode {on:false}`。）

**回退的前提**：本地库本身没被写过。所以翻转后如果门店在中心库模式下开了单，
那些单子**只在中心库**，退回本地就看不到它们 —— 回退前必须先把中心库的新单子补回本地。
