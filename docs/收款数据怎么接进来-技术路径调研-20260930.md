# 收款数据怎么接进来：技术路径调研

日期：2026-09-30
问题：老板问「我觉得应该可以把收费（收款）数据接进来的，去找找办法」

> **先改口。** 前两轮我下的结论是「个人收款码官方不给第三方开接口 → 做不到自动同步」。
> 这句话对**这一条路**仍然成立，但用来否定整件事是错的。查完有一整动物园的路，
> 至少有两条是**今天就能开工、且零门槛**的。我把结论重排如下。

---

## 一、一句话结论

**技术上完全做得到，而且不用营业执照也能做到。但要商量的是另一件事：**
**把收款数据接进来本身不产生价值——它必须和「收银台数据」比对，才有意义。**

详见第五节（这是本文档最重要的一节）。

---

## 二、四条路总表

| # | 路子 | 要不要执照 | 实时性 | 老板要做什么 | 工时 | 合规 |
|---|---|---|---|---|---|---|
| ① | 官方账单 API（已是正规商户） | 要营业执照+商户号 | **T+1**（次日 8~10 点） | 把 API 证书给我们 | ~1.5 周 | ✅ 官方 |
| ② | 小微商户 + 我们做收单服务商 | **客户不要执照**（身份证+银行卡+经营照片） | T+1 | 一次进件 | 服务商注册 1~3 月 | ✅ 官方 |
| ③ | Android 通知监听 | 不要 | **秒级实时** | 装个 App、勾两个开关 | ~1 周 | ⚠️ 灰色 |
| ④ | 账单文件导出后导入 | 不要 | 手动 | 每月导一次文件 | 0.5~1.5 天 | ✅ 官方功能 |

---

## 三、四条路分别怎么回事

### ① 官方账单 API（正规商户）—— 最稳，但要执照

微信：`GET /v3/bill/tradebill?bill_date=…` → 返回 `download_url`（有效期 5 分钟）→ 再 GET 拿 CSV。
支付宝：`alipay.data.dataservice.bill.downloadurl.query` → `bill_download_url`（**30 秒**失效）→ 下载 Excel(ZIP)。

**共同注意点：**
- 都是 **T+1**：微信次日 10 点后生成昨日账单，支付宝次日 8 点前。**当天拿不到当天的数。**
- 支付宝明确了：**不支持服务商代理商家下载账单**，只能付款方自己对接 → ②号路的支付宝侧基本封死。
- 支付宝的 `bill_type=trade` 要求已签约支付产品；`signcustomer` 要求签约「收钱码/经营码」产品。

### ② 小微商户 + 我们做服务商 —— 战略级，值得单独评估

这是本次最大的发现，也是对"必须营业执照"的直接反驳。

- **微信「小微商户」主体类型**：定义就是「无营业执照、免办理工商注册登记的商户」，材料 = **身份证 + 银行卡 + 经营照片**。适用行业**包含线下零售**（正是我们的客户画像）。费率 0.38%~0.6%。单笔上限 5000、单日 10 万。
- **但它不能自己调 API**：微信支付官方社区答复明确——**服务商模式下的子商户（特约/二级商户）不支持自行设置 APIv3 密钥和证书**。
- **账单怎么拿**：文档原话「**小微商户不单独提供对账单下载，只能通过全量账单获取**」——也就是**以服务商身份不传 `sub_mchid` 拉全量账单，里面含小微商户数据**。
- **推论**：如果我们自己去注册成**收单服务商**，把客户作为特约商户进件，就能用服务商身份统一拉全量账单。

⚠️ **这条路最大的未知是"我们能不能成为服务商"以及要多久**，不是技术问题。要单独做一次调研/咨询渠道经理。
⚠️ 支付宝侧这条不成立（官方明确不让服务商代下载）。

### ③ Android 通知监听 —— 真·实时，零门槛，但灰色

**原理**：用户授权 `NotificationListenerService` 后，读取微信/支付宝发到本机的通知文本，正则抠出金额和时间，写进我们的库。
对我们这套架构来说，最后一步就是往 `POST /api/invoke` 发一条命令而已。

GitHub 上这条已经被反复验证过（不止一个项目）：

| 项目 | 语言 | 说明 |
|---|---|---|
| `doublefishes48/AutoLedger` | Java | 通知 + 无障碍兜底 + 本地 SQLite，**README 明确写"不作为普通用户发布版本上架"** |
| `zouyahui/monay` | Kotlin | 支付宝/微信支付+转账通知解析、自动分类、自动入账 |
| `artifactcw/auto-accounts` | Java | 基于 NotificationListenerService 的自动记账 |
| `jinyule/bookkeeping`、`DykiSensei/seamless-bookkeeping` | — | AutoLedger 引用的两个前置验证项目 |

**硬边界（必须写进合同/告知客户）：**
1. **只有金额和时间** —— 没有商品、没有付款人。**解决不了"不知道卖了什么"**。
2. **只能安卓**，iOS 完全不行。
3. **上不了应用商店**（Google Play 与国内商店均大概率拒审，微信/支付宝用户协议也不允许）；只能做「自用/客户提供技术支持」的分发包。
4. **国产 ROM 可能隐藏通知正文**，需客户在系统设置里打开"显示通知详情"；App 需常驻后台、关电池优化。
5. **微信改文案就要改正则**，长期有维护成本。

### ④ 账单文件导出后导入 —— 最朴素、最稳

微信/支付宝都能导出账单 CSV/Excel。做一个「拖进来 → 解析 → 落 transaction」的功能即可，
一个月点一次。**这条没有任何合规风险，建议无论如何都要有**（作为③④失败时的兜底）。

**有现成轮子可以直接抄/移植：**

| 项目 | Stars | License | 能复用什么 |
|---|---|---|---|
| `deb-sig/double-entry-generator` | 698 | **Apache-2.0** | **现成的微信（CSV+XLSX）与支付宝 CSV 解析器**，架构是 `provider → IR → compiler`，照着它写 Node 版 parser 即可；还有 WASM 浏览器版（`deg-online`） |
| `deb-sig/bill-file-converter` | 14 | Apache-2.0 | 把各种账单文件统一转成 CSV |
| `deb-sig/deg-provider-template` | 0 | Apache-2.0 | 新增 provider 的模板 |

> License 提示：Apache-2.0 可商用，但需保留版权声明与 License 副本、标注修改。

## 四、落到代码要动哪里

无论哪条路，最后都汇到同一处：**新开一条命令**。

| 步骤 | 位置 |
|---|---|
| 新增命令 | `electron/commands/billImport.js`（建议名：`bill:import`） |
| 注册 | `electron/commandRegistry.json` |
| 字段解析 | 参考 `deb-sig/double-entry-generator` 的 `pkg/provider/wechat/`、`pkg/provider/alipay/` |
| 去重 | 以**交易单号**为唯一键做幂等（`importBatch` 已有的"坏行跳过、合法行同事务提交"思路可直接复用） |
| 对账 | 复用现有 `receipt:reconcile`（手机端已在用：`mobile/app.js:2036`） |
| 手机/桌面入口 | `mobile/pages/*.js` + `app.js` 功能列表 / `src/pages/*.tsx` |

## 五、最重要的一节：接进来 ≠ 有价值

这是我和前两轮最大的认知差。

| 客户能得到什么 | 微信自己给了吗 |
|---|---|
| 「今天微信到账 ¥1,486」 | ✅ **给了，而且实时** |
| 「昨天微信到账 ¥1,486」 | ✅ 给了 |
| 「这个月微信收到 ¥30,200」 | ✅ 给了 |

**也就是说：我们费劲把收款数据拉进来，结果给的是微信已经在给的同一个数字。增量还是 0。**

### 唯一能产生价值的用法：两条数据交叉验证

```
微信实际到账（自动拉来）  ¥1,486
收银台录入（我们自己的）  ¥1,200
─────────────────────────────
差额                    ¥286   ← 微信永远不知道这个数
```

**微信不知道你卖了什么货，所以它算不出这个差额。这是它结构性给不了的。**

而且对照痛点判定铁律 —— **今天不查，今天就会继续丢钱**：这正是"凭证"类需求（当场能拿出来对质），
不是"账目"类需求（月底算清楚）。这是个体户愿意埋单的那一类。

**落点已经现成：`receipt:reconcile`。** 只是它现在比对的是「手填的收款登记」和「营业额」，
改成自动数据后，就从"多一道手填"变成"什么都不用做，系统告诉你今天差了 286"。

## 六、建议的顺序

| 顺序 | 做什么 | 为什么 |
|---|---|---|
| **先** | 在**自家渔具店**跑一遍 ③（通知监听，1 周） | 零门槛、真实时。验证的是"差额告警"有没有存在感，而不是技术可行性 |
| **同时** | ④ 账单文件导入做兜底（0.5~1.5 天） | 无风险，随时能用 |
| **再看** | ① 官方 API（有执照的客户） | 等真出现了有执照且愿意配合的客户再说 |
| **单独评估** | ② 我们自己做收单服务商 | 战略级，涉及注册门槛与周期，不当成本周动作 |

**砍掉的想法**：不要为了"能自动同步"这个feature 本身去打动客户。客户账怕的不是「看不到微信的数字」，
是「卖了多少和收了多少对不上也说不清」。

## 七、待验证清单（别当成既定事实）

1. **小微商户能否自己下载账单**：有一份第三方资料称"特约商户自调模式下可申请 API 证书"，
   与微信官方社区"子商户不支持自行设置密钥"的答复冲突。**以微信官方答复为准，需实际验证。**
2. **我们注册收单服务商的实际门槛与周期**（ii、风控资质、保证金等）。
3. **支付宝 `signcustomer` 账单是否可用于「个人经营收款码」**（若可以，支付宝侧就有一条个人能走的官方路）。
4. 通知监听在自己的安卓机上能稳定抓到几家银行/几个版本的微信。
